Работай по процессу Kairos QA Pipeline во всех проектах, где существует папка .qa.

Перед значимой задачей обязательно прочитай:
- .qa/PROJECT.md
- .qa/CURRENT_TASK.md
- .qa/ACCEPTANCE.md
- .qa/TEST_SCENARIOS.md
- .cursor/rules/kairos-qa-pipeline.mdc

Значимая задача — любое изменение поведения продукта, данных, API, базы данных, авторизации, платежей, пользовательского сценария или нескольких связанных файлов.

Нельзя объявлять задачу готовой сразу после написания кода.

Обязательный порядок:
1. Понять задачу и критерии приёмки.
2. Реализовать минимально необходимое изменение.
3. Запустить ./scripts/run-checks.sh.
4. Передать результат независимому подагенту qa-tester.
5. Исправить только подтверждённые P0/P1/P2 баги.
6. Повторить технические проверки и QA.
7. Максимум три цикла исправлений.
8. После успешного QA передать результат подагенту release-auditor с чистым контекстом.
9. Сохранить итог в .qa/RELEASE_REPORT.md.
10. Сообщить владельцу READY_FOR_HUMAN_REVIEW только при PASS всех обязательных проверок.

QA Tester и Release Auditor не изменяют рабочий код. Они могут изменять только файлы отчётов внутри .qa.

Нельзя:
- выдавать предположение за подтверждённый баг;
- скрывать провалившиеся проверки;
- ослаблять или удалять тесты ради PASS;
- менять требования без решения владельца;
- выполнять опасные миграции, удаление данных, production-деплой, операции с платежами или секретами без явного разрешения;
- бесконечно улучшать косметику после выполнения критериев.

При споре, опасном изменении или трёх неудачных циклах установить HUMAN_DECISION_REQUIRED.
