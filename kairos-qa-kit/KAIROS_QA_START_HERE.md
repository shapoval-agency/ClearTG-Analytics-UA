# KAIROS QA — НАЧАТЬ ЗДЕСЬ

Эта памятка нужна, чтобы через месяц не вспоминать, как подключать QA-систему к новому проекту.

---

## Где что хранить

На рабочем столе желательно держать папку:

```text
TimeKairos/
├── kairos-qa-kit/
├── Новый проект 1/
├── Новый проект 2/
└── ...
```

Внутри `kairos-qa-kit` лежат установщики:

```text
install.sh
install-many.sh
GLOBAL_USER_RULE.txt
template/
```

Не копируй папку `template` вручную в проект. Используй установщик.

---

# НОВЫЙ ПРОЕКТ — ЧТО ДЕЛАТЬ

## Вариант 1. Установить QA в один новый проект

Открой Terminal и выполни:

```bash
cd ~/Desktop/TimeKairos/kairos-qa-kit
./install.sh "/полный/путь/к/новому/проекту"
```

Проще всего:

1. Напечатай:

```bash
./install.sh 
```

2. После пробела перетащи папку проекта из Finder в Terminal.
3. Нажми Enter.

Пример:

```bash
./install.sh "/Users/koristuvac/Desktop/TimeKairos/New Project"
```

---

## Вариант 2. Установить QA сразу во все проекты общей папки

```bash
cd ~/Desktop/TimeKairos/kairos-qa-kit
./install-many.sh "/Users/koristuvac/Desktop/TimeKairos"
```

Скрипт найдёт проекты по файлам:

```text
.git
package.json
composer.json
pyproject.toml
wp-config.php
```

Он проверяет только подпапки первого уровня.

# ПОСЛЕ УСТАНОВКИ В НОВЫЙ ПРОЕКТ

Открой проект в Cursor.

В Terminal проекта выполни:

```bash
./scripts/qa-doctor.sh
```

Ожидаемый результат:

```text
QA kit installed correctly.
```

Затем отправь Cursor этот промпт:

```text
Проанализируй текущий проект целиком.

Рабочий код пока не изменяй.

Заполни на основании реального устройства проекта:

- .qa/PROJECT.md
- .qa/ACCEPTANCE.md
- .qa/TEST_SCENARIOS.md
- .qa/CHECKS.conf

Не придумывай отсутствующие команды, функции и возможности.
Проверь package.json, composer.json, структуру проекта, документацию и существующие тесты.

После заполнения запусти:

./scripts/qa-doctor.sh
./scripts/run-checks.sh

В конце покажи кратко:
1. как запускается проект;
2. какие проверки настроены;
3. какие ключевые сценарии добавлены;
4. что требует моего уточнения.

Рабочий код продукта не менять.
```

После ответа Cursor проверь только одно: правильно ли он понял, что делает продукт.

# КАК СОЗДАТЬ НОВУЮ ЗАДАЧУ

В Terminal проекта:

```bash
./scripts/new-qa-task.sh "Название задачи"
```

Пример:

```bash
./scripts/new-qa-task.sh "Добавить экспорт отчёта в PDF"
```

Открой файл:

```text
.qa/CURRENT_TASK.md
```

Заполни:

- проблему;
- требуемый результат;
- критерии приёмки;
- что нельзя менять;
- важные риски.

После этого отправь Cursor:

```text
Выполни задачу из .qa/CURRENT_TASK.md.
После реализации запусти полный Kairos QA Pipeline.

Обязательный цикл:
реализация → технические проверки → QA Tester → исправления → повторный QA → Release Auditor.

Не объявляй задачу готовой без PASS в .qa/RELEASE_REPORT.md.
```

---

# ЧТО ПРОИСХОДИТ БЕЗ ТЕБЯ

```text
Cursor пишет код
        ↓
запускает технические проверки
        ↓
QA Tester ищет подтверждённые баги
        ↓
Cursor исправляет
        ↓
QA Tester проверяет повторно
        ↓
Release Auditor делает финальную приёмку
        ↓
тебе остаётся ручная проверка
```

Максимум три цикла исправлений.

После трёх неудачных циклов система должна остановиться со статусом:

```text
HUMAN_DECISION_REQUIRED
```

# ГДЕ СМОТРЕТЬ РЕЗУЛЬТАТ

Главный файл:

```text
.qa/RELEASE_REPORT.md
```

Быстрый статус:

```bash
./scripts/qa-status.sh
```

Технические проверки:

```text
.qa/LAST_CHECKS.md
```

Баги:

```text
.qa/BUGS.md
```

Отчёт тестировщика:

```text
.qa/QA_REPORT.md
```

---

# КОГДА МОЖНО ИДТИ ПРОВЕРЯТЬ РУКАМИ

Только когда в отчётах:

```text
CHECKS_VERDICT: PASS
QA_VERDICT: PASS
RELEASE_VERDICT: PASS
```

И нет открытых:

```text
P0
P1
P2
```

`P3` — мелкие замечания. Они не обязаны блокировать выпуск.

---

# ГЛОБАЛЬНОЕ ПРАВИЛО CURSOR

Файл:

```text
kairos-qa-kit/GLOBAL_USER_RULE.txt
```

Его нужно вставить в глобальные User Rules Cursor только один раз.

Если меняешь компьютер или переустанавливаешь Cursor:

```text
Cursor → Settings → Rules → User Rules
```

Скопируй туда содержимое `GLOBAL_USER_RULE.txt`.

---

# ЕСЛИ ПАПКА ПРОЕКТА УЖЕ СОДЕРЖИТ QA-ФАЙЛЫ

Обычная установка не перезаписывает существующие файлы:

```bash
./install.sh "/путь/к/проекту"
```

Для принудительного обновления пакета:

```bash
./install.sh --force "/путь/к/проекту"
```

Осторожно: `--force` может перезаписать заполненные QA-файлы.

Перед принудительным обновлением сделай копию папки `.qa`.

---

# ЧЕГО НЕ ДЕЛАТЬ

Не нужно:

- вручную копировать содержимое `template`;
- ставить пакет только в общую папку, если проекты открываются отдельно;
- разрешать QA Tester самостоятельно менять рабочий код;
- запускать бесконечные циклы исправлений;
- считать фразу Cursor «всё готово» доказательством;
- выполнять реальные платежи, production-деплой и удаление данных без ручного подтверждения.

# САМАЯ ВАЖНАЯ МЫСЛЬ

Cursor у тебя один, но каждый проект — отдельная папка.

Поэтому:

```text
Глобальные User Rules — один раз в Cursor.
QA Kit — отдельно в корень каждого проекта.
PROJECT.md и сценарии — свои для каждого проекта.
```
