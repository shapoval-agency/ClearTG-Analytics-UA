# KAIROS QA — КАК ЭТИМ ПОЛЬЗОВАТЬСЯ

Эта инструкция объясняет простыми словами, что делать с новым или существующим проектом.

---

# САМАЯ ПРОСТАЯ СХЕМА

```text
Создал или открыл проект
        ↓
один раз установил QA Kit
        ↓
Cursor изучил проект и заполнил паспорт
        ↓
один раз добились зелёных базовых проверок
        ↓
для каждой новой задачи создаём CURRENT_TASK
        ↓
Cursor делает → QA проверяет → Cursor исправляет
        ↓
Release Auditor принимает
        ↓
ты проверяешь руками
```

---

# ВАЖНО ПОНЯТЬ

У тебя один Cursor, но каждый проект находится в своей папке.

Поэтому:

```text
Глобальные правила Cursor — устанавливаются один раз.
QA Kit — устанавливается в каждую папку проекта.
Паспорт и тесты — отдельные для каждого проекта.
```

---

# СИТУАЦИЯ 1. У ТЕБЯ УЖЕ ЕСТЬ ПРОЕКТ

## Шаг 1. Установить QA Kit

Открой Terminal:

```bash
cd ~/Desktop/TimeKairos/kairos-qa-kit
```

Затем:

```bash
./install.sh "/полный/путь/к/проекту"
```

Можно после `./install.sh ` просто перетащить папку проекта из Finder в Terminal.

Пример:

```bash
./install.sh "/Users/koristuvac/Desktop/TimeKairos/TimeKairos SEO"
```

## Шаг 2. Открыть проект в Cursor

Открывай именно папку проекта, а не общую папку со всеми проектами.

## Шаг 3. Проверить установку

В Terminal внутри проекта:

```bash
./scripts/qa-doctor.sh
```

Правильный результат:

```text
QA kit installed correctly.
```

## Шаг 4. Попросить Cursor изучить проект

Отправь Cursor:

```text
Проанализируй текущий проект целиком.

Рабочий код пока не изменяй.

Заполни на основании реального устройства проекта:

- .qa/PROJECT.md
- .qa/ACCEPTANCE.md
- .qa/TEST_SCENARIOS.md
- .qa/CHECKS.conf

Не придумывай отсутствующие команды, функции и возможности.
Проверь package.json, composer.json, структуру проекта, документацию и существующие тесты.

После заполнения запусти:

./scripts/qa-doctor.sh
./scripts/run-checks.sh

В конце покажи кратко:
1. как запускается проект;
2. какие проверки настроены;
3. какие ключевые сценарии добавлены;
4. что требует моего уточнения.

Рабочий код продукта не менять.
```

## Шаг 5. Добиться зелёной базы

До новых функций нужно получить:

```text
CHECKS_VERDICT: PASS
```

Если старые lint, test или build проверки падают, сначала отдельной задачей исправить их.

После этого проект готов к нормальной работе через QA-конвейер.

# СИТУАЦИЯ 2. ТЫ СОЗДАЁШЬ НОВЫЙ ПРОЕКТ

## Шаг 1. Создать папку проекта

Например:

```text
/Users/koristuvac/Desktop/TimeKairos/New Product
```

## Шаг 2. Открыть эту папку в Cursor

Скажи Cursor, что нужно создать: сайт, плагин, сервис или приложение.

Пусть он сначала создаст базовую структуру проекта:

```text
package.json
или
composer.json
или
другие основные файлы
```

## Шаг 3. Установить QA Kit

В другом окне Terminal:

```bash
cd ~/Desktop/TimeKairos/kairos-qa-kit
./install.sh "/Users/koristuvac/Desktop/TimeKairos/New Product"
```

## Шаг 4. Проверить установку

В Terminal нового проекта:

```bash
./scripts/qa-doctor.sh
```

## Шаг 5. Заполнить паспорт нового проекта

Отправь Cursor тот же промпт первичного анализа:

```text
Проанализируй текущий проект целиком.

Рабочий код пока не изменяй.

Заполни:

- .qa/PROJECT.md
- .qa/ACCEPTANCE.md
- .qa/TEST_SCENARIOS.md
- .qa/CHECKS.conf

Не придумывай отсутствующие функции.

После заполнения запусти:
./scripts/qa-doctor.sh
./scripts/run-checks.sh
```

## Шаг 6. Проверить, правильно ли Cursor понял продукт

Тебе нужно проверить только:

- что делает продукт;
- кто им пользуется;
- какой главный результат;
- какие функции критические;
- что нельзя ломать;
- что пока не входит в проект.

После этого можно начинать разработку задачами.

# КАК РАБОТАТЬ КАЖДЫЙ ДЕНЬ

Для каждой новой функции или исправления создаётся отдельная задача.

## Шаг 1. Создать задачу

В Terminal проекта:

```bash
./scripts/new-qa-task.sh "Название задачи"
```

Пример:

```bash
./scripts/new-qa-task.sh "Добавить экспорт отчёта в PDF"
```

Скрипт создаст новый файл:

```text
.qa/CURRENT_TASK.md
```

Старые отчёты сохранит в архив.

## Шаг 2. Описать задачу

Открой:

```text
.qa/CURRENT_TASK.md
```

Нужно заполнить:

```text
Проблема
Что должно получиться
Что разрешено менять
Что нельзя менять
Критерии готовности
Риски
```

Можно попросить Cursor подготовить черновик:

```text
На основании моего описания заполни .qa/CURRENT_TASK.md.

Пока не меняй рабочий код.

Задача:
[сюда написать обычными словами, что нужно сделать]

Сформулируй:
- проблему;
- требуемый результат;
- scope;
- out of scope;
- критерии приёмки;
- риски.

После заполнения остановись и покажи мне документ на согласование.
```

Ты быстро читаешь файл и подтверждаешь, что Cursor правильно понял задачу.

## Шаг 3. Запустить полный цикл

Отправь Cursor:

```text
Выполни задачу из .qa/CURRENT_TASK.md.

После реализации запусти полный Kairos QA Pipeline:

1. технические проверки;
2. QA Tester;
3. исправление подтверждённых P0/P1/P2;
4. повторные проверки;
5. повторный QA;
6. Release Auditor.

Не объявляй задачу готовой без:
CHECKS_VERDICT: PASS
QA_VERDICT: PASS
RELEASE_VERDICT: PASS

Максимум три цикла исправлений.
После трёх неудачных циклов установи HUMAN_DECISION_REQUIRED.
```

После этого не нужно переносить замечания между чатами.

Cursor должен сам:

```text
сделать
→ проверить
→ найти баги
→ исправить
→ проверить повторно
→ провести финальный аудит
```

# ЧТО ДЕЛАТЬ, КОГДА CURSOR ЗАКОНЧИЛ

## Шаг 1. Посмотреть статус

В Terminal проекта:

```bash
./scripts/qa-status.sh
```

Хороший результат:

```text
CHECKS_VERDICT: PASS
QA_VERDICT: PASS
OPEN_P0: 0
OPEN_P1: 0
OPEN_P2: 0
RELEASE_VERDICT: PASS
```

## Шаг 2. Открыть главный отчёт

```text
.qa/RELEASE_REPORT.md
```

Смотри:

- что изменили;
- что проверили;
- какие риски остались;
- что нужно проверить тебе руками.

## Шаг 3. Проверить продукт самостоятельно

Твоя ручная проверка нужна для:

- логики бизнеса;
- удобства;
- визуального ощущения;
- реальных данных;
- того, соответствует ли результат твоей задумке.

Ты уже не должен искать 30 технических багов. До тебя должны дойти только минимальные спорные моменты.

# ЕСЛИ НУЖНО ПРОСТО ИСПРАВИТЬ БАГ

Создай задачу:

```bash
./scripts/new-qa-task.sh "Исправить потерю данных после обновления"
```

Потом дай Cursor:

```text
Заполни .qa/CURRENT_TASK.md для этого бага.

Проблема:
[опиши обычными словами]

Сначала зафиксируй шаги воспроизведения и ожидаемый результат.
Потом реализуй исправление и запусти полный Kairos QA Pipeline.
Обязательно проверь регрессию соседних сценариев.
```

---

# ЕСЛИ CURSOR НЕ ЗАПУСТИЛ QA-АGЕНТОВ САМ

Напиши:

```text
Ты остановился после реализации.

Продолжи обязательный Kairos QA Pipeline:

1. запусти ./scripts/run-checks.sh;
2. вызови подагента qa-tester;
3. исправь подтверждённые P0/P1/P2;
4. повторно вызови qa-tester;
5. после QA PASS вызови release-auditor;
6. сохрани итог в .qa/RELEASE_REPORT.md.
```

---

# ЕСЛИ ПРОВЕРКИ ПАДАЮТ

Не игнорируй это.

```text
lint FAIL
tests FAIL
build FAIL
```

означает, что задача пока не готова.

Скажи Cursor:

```text
Не продолжай развитие функций.

Сначала найди причину провалившихся проверок.
Не отключай правила и не удаляй тесты ради PASS.
Исправь первопричину и повтори полный набор проверок.
```

---

# ЧТО ОЗНАЧАЮТ СТАТУСЫ

## PASS

Всё обязательное прошло. Можно проверять руками.

## FAIL

Есть подтверждённая проблема. Cursor должен исправить.

## BLOCKED

Проверку невозможно выполнить: нет среды, данных, команды или доступа.

## HUMAN_DECISION_REQUIRED

Агенты не должны решать сами. Требуется твоё решение.

Например:

- удаление данных;
- изменение платежей;
- опасная миграция;
- спорная бизнес-логика;
- реальные секреты;
- четвёртый цикл исправлений.

---

# КРИТИЧНОСТЬ БАГОВ

```text
P0 — продукт не работает, потеря данных, серьёзная безопасность.
P1 — основной сценарий сломан или данные неверные.
P2 — важная функция работает неправильно, но обход есть.
P3 — косметика и мелкое неудобство.
```

Для выпуска должно быть:

```text
P0 = 0
P1 = 0
P2 = 0
```

P3 можно оставить на потом.

.qa/RELEASE_REPORT.md

# ГЛАВНОЕ ПРАВИЛО

Не говори Cursor просто:

```text
Сделай функцию.
```

Говори:

```text
Сначала зафиксируй задачу и критерии.
Потом реализуй.
Потом запусти полный Kairos QA Pipeline.
```

Так Cursor не остановится сразу после написания кода.
