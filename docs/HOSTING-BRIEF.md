# Бріф для пошуку хостингу бека (ClearTG Analytics UA)

Документ для передачі людині, яка підбирає новий хостинг замість поточного українського — щоб не пояснювати стек словами щоразу.

## Навіщо переїзд

Поточний бек стоїть на хостингу в Україні. Причини шукати заміну (типово для таких кейсів — уточнити чи актуально):

- Ризик даунтайму через відключення світла / інтернету
- Потрібна стабільна робота 24/7 (Telegram webhook, черги CAPI/GA4/TikTok не можуть просто "полежати")
- Можливо потрібне зберігання даних у ЄС (проєкт має privacy-by-design / consent-логіку)

## Що саме треба хостити

Бек — це **не serverless-функція**, а довготривалий процес + сховища:

| Компонент | Технологія | Примітка |
|---|---|---|
| API | NestJS + Fastify (Node.js ≥20) | має працювати постійно, не "засинати" (webhook від Telegram і крон-джоби) |
| База даних | PostgreSQL 16 | через Prisma ORM |
| Черги / cron | Redis 7 + BullMQ | погодинний retention-чек (D1/D7/D30), відправка подій у рекламні API |
| Telegram-бот | grammY (Bot API, вебхук) | потрібен публічний HTTPS-ендпоінт `/telegram/webhook` |
| Фронтенд (кабінет) | Next.js 15 | **вже на Vercel, переносити не треба** — цей бріф лише про бек (API + БД + Redis) |

Джерело правди по стеку: [README.md](../README.md#стек).

## Як зараз пакується / деплоїться

- Є `Dockerfile.api` — образ бека вже готовий, будь-який хостинг з підтримкою Docker-контейнера підійде без переписування
- Є `docker-compose.yml` — Postgres + Redis для локалки/staging, той самий compose можна підняти і на VPS
- Є `railway.toml` — зараз staging піднятий на Railway (Dockerfile-білд, healthcheck `/health`); це не обов'язково має лишатись Railway, просто поточний приклад конфіга
- Health-check ендпоінт: `GET /health`
- Порт API: `3001` (з env `API_PORT`)

## Обов'язкові вимоги до нового хостингу

- [ ] Підтримка Docker-контейнера (є готовий `Dockerfile.api`) **або** голий VPS з Docker
- [ ] Керована або самостійно піднята PostgreSQL 16 (з можливістю робити бекапи)
- [ ] Керований або самостійно піднятий Redis 7 (для BullMQ-черг)
- [ ] Постійний процес (не serverless / не "cold start" за запитом) — бо є вебхук Telegram і погодинні крони
- [ ] Публічний домен з HTTPS (для вебхука Telegram і серверних викликів Meta CAPI / GA4 / Google Ads / TikTok)
- [ ] Можливість задати ENV-змінні (секрети: `JWT_SECRET`, `ENCRYPTION_KEY`, `HASH_SALT`, `TELEGRAM_BOT_TOKEN` та інше — повний список у [.env.example](../.env.example))
- [ ] Вихідний SMTP або дозволений вихідний трафік на порт SMTP (magic-link листи, запрошення в агенцію)
- [ ] Логи доступні через веб-панель або CLI (для дебагу вебхуків/інтеграцій)

## Бажано, але не критично

- [ ] Дата-центр у ЄС (через privacy-by-design/consent-логіку проєкту — уточнити наскільки це вимога, а не побажання)
- [ ] Автодеплой з GitHub (push → деплой), як зараз на Railway
- [ ] Окремий staging-контур (є `docker-compose.staging.yml` і `.env.staging.example`)
- [ ] Прозорий білінг без різких стрибків ціни при рості навантаження

## Орієнтовне навантаження (для підбору тарифу/розміру інстансу)

- Старт: невеликий SaaS, MVP-стадія, немає високого RPS
- Основне навантаження — не веб-трафік, а фонові джоби (погодинний retention-чек підписників через Telegram Bot API, відправка конверсій у рекламні кабінети)
- Мінімально достатньо: 1 інстанс API (1 vCPU / 1–2 GB RAM), Postgres невеликого розміру, Redis невеликого розміру — з можливістю збільшити пізніше

## Що НЕ входить у цей переїзд

- Фронтенд-кабінет (`apps/web`) — лишається на Vercel
- Домен для кабінету — лишається як є
