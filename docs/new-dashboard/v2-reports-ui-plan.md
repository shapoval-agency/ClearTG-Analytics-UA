## 1. Пользовательский сценарий

**Основной — трафик-менеджер после запуска рекламы:**

```
запустил рекламу →
создал трекинговую ссылку под источник →
получил первые клики →
получил первых подписчиков →
открыл «Звіти» →
увидел по каждому источнику: сколько пришло, сколько дошло до Telegram, сколько осталось →
понял результат — продолжать или останавливать
```

**Владелец канала без активной рекламы (открыл раздел впервые):**

```
подключил канал →
ещё не создавал ни одной ссылки →
открыл «Звіти» →
видит не пустую таблицу, а объяснение «Ви ще не запускали рекламу» со ссылкой на «Посилання» →
понимает, что делать дальше
```

**Проверка результата за период:**

```
открыл «Звіти» →
выбрал период «7 днів» →
посмотрел, изменились ли цифры →
переключил канал (если их несколько) →
убедился, что данные именно по этому каналу
```

## 2. Структура страницы

Три блока поверх общих фильтров — не шесть страниц старого кабинета и не отдельная страница на каждый разрез.

```
┌───────────────────────────────────────────────────┐
│ Звіти                                              │
│ Яке джерело працює і наскільки добре.              │
├───────────────────────────────────────────────────┤
│ [ Період: Увесь час ▾ ]   [ Канал: Усі канали ▾ ]  │  ← фільтри, стан в URL
├───────────────────────────────────────────────────┤
│  Кліки │ Дійшли │ Підписки │ Відписки │ Приріст │ CR│  ← 1. верхній блок, 6 чисел
├───────────────────────────────────────────────────┤
│  Джерела                                           │  ← 2. кампанії, розріз по джерелу
│  ─────────────────────────────────────────         │
│  Назва кампанії | Кліки | Дійшли | Підписки | ...  │
│  ...                                               │
│  Джерело невідоме | — | — | N підписок             │  ← чесний залишок, не кампанія
├───────────────────────────────────────────────────┤
│  Посилання                                         │  ← 3. розріз по посиланню
│  Назва/slug | Кліки | Підписники | Ефективність    │
└───────────────────────────────────────────────────┘
```

### Чому саме так, а не «источники + кампании + ссылки + качество данных» четырьмя блоками

В брифе структура предложена как 5 концептов (главные показатели, источники, кампании, ссылки, качество данных). На данных backend «источники» и «кампании» — **одно и то же**: `GET /api/dashboard/campaigns` группирует ровно по кампании, а кампания в этом продукте и есть источник трафика (платформа + название). Разводить их на два визуальных блока значило бы показывать одну и ту же таблицу дважды.

«Качество данных» как отдельный блок (донат по 5 типам атрибуции — EXACT/CAMPAIGN/PROBABILISTIC/ORGANIC/UNKNOWN) в эту итерацию **не входит** — это осознанное сужение, а не забытый пункт. Вместо отдельного визуального блока честность данных встроена в сам блок «Джерела»: если сумма подписчиков по кампаниям меньше общего числа подписчиков из верхнего блока — разница показана отдельной строкой «Джерело невідоме», а не спрятана. Это и есть требование брифа «не показывать источник, если данные неизвестны» и «использовать UNKNOWN корректно» — только на уровне строки, а не отдельного графика. Полный разбор по 5 типам атрибуции остаётся в `v2-reports-plan.md` как следующий шаг (там он уже описан).

Лента отдельных подписок/отписок (кто именно пришёл/ушёл) — тоже не в этой итерации: бриф просит три блока (показатели, Джерела, Посилання), лента — это ответственность `/v2/subscribers`, который эту задачу не трогает.

### Что не переносим из старого кабинета

Шесть раздельных страниц `/reports/*` без общих фильтров, технические подписи колонок, страницу качества атрибуции как отдельный пункт меню (`/reports/attribution-confidence` не была даже в меню старого кабинета).

## 3. API mapping

Все четыре запроса уже готовы, ничего нового не добавляется. Один и тот же `from/to/channelId` передаётся во все три отчётных.

| Блок UI | API | Данные |
|---|---|---|
| Фильтр «Канал» (список) + проверка «есть ли подключённые каналы» | `GET /api/channels` | `id`, `title`, `username`, `isActive` |
| Верхний блок (6 показателей) | `GET /api/dashboard/overview?from=&to=&channelId=` | `clicks`, `reached`, `reachRate`, `subscribers`, `unsubscribes`, `clickToSubscribeRate` (прирост = `subscribers − unsubscribes`, считается на фронте из тех же двух чисел) |
| Джерела | `GET /api/dashboard/campaigns?from=&to=&channelId=` | по строке: `name`, `channelTitle`, `clicks`, `reached`, `reachRate`, `subscribers`, `unsubscribes`, `conversionRate`. Строка «Джерело невідоме» — `overview.subscribers − Σ(subscribers по строкам)`, считается на фронте |
| Посилання | `GET /api/dashboard/tracking-links?from=&to=&channelId=` | по строке: `slug`, `name`, `campaignName`, `clicks`, `subscribers`, `conversionRate` (= «эффективность») |

## 4. Состояния интерфейса

| Состояние | Когда | Что показываем |
|---|---|---|
| `loading` | `loading.tsx`, пока грузятся все четыре запроса | Текст загрузки, тот же паттерн, что в `/v2/links` |
| `disconnected` | Каналов вообще нет (`GET /api/channels` — пусто) | «Спочатку підключіть канал» + ссылка на «Канали» (тот же текст, что уже есть в `/v2/links`) |
| `empty` (нет рекламы) | Каналы есть, но `overview.clicks === 0` за всё время (без учёта фильтра) | «Ви ще не запускали рекламу» + объяснение + ссылка на «Посилання», чтобы создать первую ссылку |
| `empty` (фильтр) | Данные в целом есть, но за выбранный период/канал — 0 кликов | «За цей період даних немає» + подсказка расширить период, **без** ссылки на «Посилання» — это другой случай |
| `error` | Любой из четырёх запросов упал (кроме 401) | Человеческий текст + «Оновіть сторінку» — тот же подход, что в `/v2/links`, без нового retry-механизма |
| `error` (сессия) | 401 / `AuthError` | «Сесія завершилася» + ссылка на `/login?next=/v2/reports` |
| `success` | Есть данные | Три блока из раздела 2 |

Пустые под-состояния внутри `success` (например, кампаний ещё нет, но клики уже есть через обычную ссылку) — не отдельный экран, а одна строка текста внутри соответствующего блока, без прерывания всей страницы.
