# MIGRATION_MAP — карта переноса функционала

> Статус каждой функции из бэклога: что переносим, что делаем заново, что создаём с нуля, что не переносим.

**Статусы предварительные.** Они проставлены по результатам анализа кода на 2026-09-10 и служат рабочей гипотезой. Финальное решение по каждому ID принимает руководитель/эксперт и фиксирует в [`DECISIONS.md`](./DECISIONS.md).

| Статус | Значение |
|---|---|
| **NEW** | Новая функция — в старом кабинете нет |
| **MIGRATE** | Переносится: логика рабочая, переиспользуем |
| **REBUILD** | Создаётся заново: функция есть, но архитектура или UX не годятся |
| **REMOVE** | Не переносится |

Легенда готовности: ✅ работает · ⚠️ частично / с оговорками · ❌ нет

### Выводы

1. **Ядро продукта переносится, а не переписывается.** На первом этапе 16 из 26 задач — MIGRATE. Атрибуция, захват клика, invite-ссылки и доставка конверсий уже работают.
2. **Больше всего нового — в этапах 04 и 05** (18 из 24 задач). Это ожидаемо: автоматизация и масштабирование в старом кабинете почти не начинались.
3. **REBUILD концентрируется в двух местах**: подача данных в интерфейсе (этапы 01–02) и надёжность доставки конверсий (этап 03).
4. **Новых таблиц почти не нужно.** Схема уже покрывает заявки в закрытый канал, reach-событие, рассылки, API-ключи, задержку конверсии и суперцели.

## Как обновлять этот файл

1. Статус меняется только вместе с записью в [`DECISIONS.md`](./DECISIONS.md).
2. Перед сменой статуса перепроверить код: оценки аудита от 2026-07-20 местами устарели в лучшую сторону.
3. Реализованные задачи не удалять из таблицы — помечать в комментарии дату и коммит.
