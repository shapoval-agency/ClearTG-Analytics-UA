## 1. Атрибуция

### 1.1 Как сейчас определяется источник

Точка входа — [attribution.service.ts](../../apps/api/src/attribution/attribution.service.ts), чистая логика — [packages/shared/src/attribution.ts](../../packages/shared/src/attribution.ts).

```
Подписка (MembershipEvent SUBSCRIBE)
   │
   ├─ определить окно атрибуции
   │    кампания invite-ссылки → её attribution_window_minutes
   │    иначе → последняя созданная активная кампания канала
   │    иначе → 10080 минут (7 дней)
   │
   ├─ выбрать кандидатов: клики канала в окне, ORDER BY clicked_at DESC, LIMIT 50
   │
   └─ attributeSubscription() — пять шагов сверху вниз:
        1. EXACT_CLICK_INVITE   0.98  invite создан под конкретный клик, клик найден в окне
        2a. CAMPAIGN_INVITE     1.00  standalone-инвайт без клика и без tracking-ссылки
        2b. CAMPAIGN_INVITE     0.82  инвайт кампании + ближайший клик той же кампании
            CAMPAIGN_INVITE     0.65  инвайт кампании, подходящего клика нет
        3. PROBABILISTIC   0.72…0.20  ближайший клик в окне; уверенность падает
                                       с ростом дистанции и числа кандидатов
        4. ORGANIC              0.50  кликов в окне нет вообще
        5. UNKNOWN              0.10  клики есть, но ни один не подошёл
```

Результат — одна запись `Attribution` на событие подписки: тип, `confidenceScore`, текстовый `reason`.

**Что здесь сделано правильно:** шаг 2a возвращает уверенность 1.0, потому что Telegram сам сообщает, какая invite-ссылка использована при вступлении. Это факт, а не расчёт. Продукт честно различает «знаю» и «предполагаю».

### 1.2 Где могут появляться ошибки

#### Ошибка A — потеря точной атрибуции при большом объёме кликов

**Механизм.** [attribution.service.ts:41](../../apps/api/src/attribution/attribution.service.ts#L41) берёт `take: 50` последних кликов в окне. Шаг 1 ищет среди них клик по `inviteLinkUsed.clickEventId`:

```ts
const matchedClick = recentClicks.find((c) => c.id === inviteLinkUsed.clickEventId);
```

Если исходный клик человека **не попал в эти 50** — а окно по умолчанию 7 дней — `find` вернёт `undefined`. Шаг 2a требует `!clickEventId`, шаг 2b тоже — оба не сработают. Логика дойдёт до шага 3 и назначит подписку **ближайшему чужому клику**.

**Это не понижение уверенности, а неверный источник.** Подписка, пришедшая из объявления A, будет засчитана объявлению B.

**Состояние сейчас:** максимум кликов в 7-дневном окне на канал — **28**. Порог не пройден. Но 28 кликов пришли за один день (2026-09-09) — при двух активных днях лимит будет превышен.

```sql
SELECT max(cnt) FROM (
  SELECT c1.id, (SELECT count(*) FROM click_events c2
                 WHERE c2.channel_id = c1.channel_id
                   AND c2.clicked_at BETWEEN c1.clicked_at - interval '7 days' AND c1.clicked_at) AS cnt
  FROM click_events c1) t;
-- 28
```

**Что делать:** при реализации отчётов не полагаться на `take: 50`. Точный клик нужно доставать прицельно — по `inviteLinkUsed.clickEventId`, а не искать в выборке последних 50. Это правка в существующем сервисе, не новая логика.

#### Ошибка B — окно атрибуции зависит от произвольной кампании

**Механизм.** [attribution.service.ts:27-32](../../apps/api/src/attribution/attribution.service.ts#L27): если у invite-ссылки нет кампании, берётся

```ts
this.prisma.campaign.findFirst({
  where: { channelId: event.channelId, isActive: true },
  orderBy: { createdAt: 'desc' },
})
```

— то есть **последняя созданная активная кампания канала**. При нескольких активных кампаниях с разными окнами результат зависит от порядка создания, а не от смысла.

На сам источник это не влияет: `campaignId` в результате берётся из клика. Но влияет на **ширину окна**, а значит на то, попадёт клик в атрибуцию или нет.

**Состояние сейчас:** на одном канале **2 активные кампании**, у обеих окно 10080 минут. Пока разницы нет — риск структурный, не проявленный.

```sql
SELECT c.channel_id, count(*) FILTER (WHERE c.is_active) AS active,
       array_agg(DISTINCT c.attribution_window_minutes) AS windows
FROM campaigns c GROUP BY 1;
-- cmqs6o0mk...  1  {10080}
-- cmr1ugzd3...  2  {10080}
```

**Что делать:** проверить сценарий до того, как у клиента появятся кампании с разными окнами.

#### Ошибка C — тихая потеря атрибуции при рассинхроне схемы

Разобрана в разделе 2.3.

### 1.3 Какие сценарии проверить

|---|---|---|
| A1 | Клик по трекинговой ссылке → подписка | `EXACT_CLICK_INVITE`, `confidence 0.98` |
| A2 | Подписка по standalone-инвайту (посев) | `CAMPAIGN_INVITE`, `confidence 1.0` |

| A7 | Клик в 23:59, подписка в 00:01 | Границы окна считаются по UTC, без сдвига на Europe/Kyiv |

## 2. Resubscribe

Человек подписался по рекламе A, отписался, подписался снова по рекламе B. Если система не создаст новое событие, она продолжит показывать источник A — агентство отчитается неверными данными.

Это была находка P0 в аудите от 2026-07-20.

### 2.1 processSubscribe

[telegram.service.ts:444-513](../../apps/api/src/telegram/telegram.service.ts#L444)

```
1. Найти ПОСЛЕДНИЙ профиль (workspace, channel, telegramUserId), ORDER BY subscribed_at DESC
2. Если у него НЕТ отписок → выйти            ← дедупликация повторных chat_member
   Если отписки ЕСТЬ → это resubscribe, продолжить
3. Найти invite по telegramInviteUrl
4. Создать MembershipEvent (SUBSCRIBE)
5. Создать SubscriberProfile
   └─ catch P2002 → залогировать и ВЫЙТИ     ← опасное место, см. 2.3
6. attributeMembership()
7. createSubscribeEvent()
```

**Проверено в коде:** шаг 2 выходит только если у последнего профиля нет отписки. Повторная подписка после отписки создаёт новую цепочку событий. ✅

### 2.2 Создание SubscriberProfile и MembershipEvent

Уникальное ограничение снято на уровне схемы — [schema.prisma:476-479](../../packages/database/prisma/schema.prisma#L476):

```prisma
// Немає @@unique — одна людина може мати кілька профілів для одного каналу,
// по одному на кожен цикл підписка→відписка→повторна підписка (resubscribe).
// "Активний" профіль — той, що ще не має пов'язаної UnsubscribeEvent.
@@index([workspaceId, channelId, telegramUserId])
```

**Проверено в живой БД** — ограничения нет, индекс обычный:

```sql
SELECT count(*) FROM pg_indexes
WHERE tablename='subscriber_profiles'
  AND indexdef LIKE '%UNIQUE%' AND indexdef LIKE '%telegram_user_id%';
-- 0  ✅
```

Существующие индексы: `subscriber_profiles_pkey`, `subscriber_profiles_membership_event_id_key` (уникальный по `membership_event_id` — так и задумано, один профиль на событие), и обычный составной индекс. Схема БД соответствует коду. ✅

> ⚠️ Проверена **только локальная база**. На staging и production схема приводится тем же `prisma db push` без истории миграций — там ограничение может быть живо. **Запустить тот же запрос на обеих базах до продолжения.**

### 2.3 Главный остаточный риск — тихий выход без атрибуции

LEFT JOIN attributions a ON a.membership_event_id = me.id

## 3. Unknown source

### 3.1 Когда появляется UNKNOWN

`UNKNOWN` — последний шаг, когда все предыдущие не сработали ([attribution.ts](../../packages/shared/src/attribution.ts), шаг 5):

```
клики канала в окне ЕСТЬ, но:
  ├─ invite не привязан к клику ИЛИ клик не найден среди 50 кандидатов
  ├─ инвайт не относится к кампании
  └─ ни один клик не прошёл withinWindow()
→ UNKNOWN, confidence 0.10
```

Отличие от `ORGANIC`: `ORGANIC` (шаг 4) означает «кликов в окне не было вообще» — подписка пришла не из отслеживаемой рекламы. `UNKNOWN` означает «клики были, но связать не удалось».

**Это разные вещи, и продукт правильно их различает.** `ORGANIC` — ответ. `UNKNOWN` — признание незнания.

### 3.2 Что показали данные

```sql
SELECT attribution_type, count(*), round(avg(confidence_score)::numeric,2) FROM attributions GROUP BY 1;
```

| Тип | Кол-во | Средняя уверенность |
|---|---:|---:|
| `EXACT_CLICK_INVITE` | 1 | 0.98 |
| `PROBABILISTIC` | 1 | 0.62 |

`UNKNOWN` и `ORGANIC` не встречаются — объём данных слишком мал, чтобы судить о доле неизвестного.

### 3.3 Может ли система назначить неправильный источник

**Да, в двух случаях.** Оба — не про `UNKNOWN`, а про то, что система выдаёт уверенный ответ вместо честного «не знаю».

#### Случай 1 — переполнение выборки кандидатов (ошибка A)

Точный клик не попал в 50 кандидатов → шаг 1 промахивается → шаг 3 назначает **ближайший чужой клик** как `PROBABILISTIC` с уверенностью до 0.72.

Правильным поведением был бы `UNKNOWN`. Вместо этого продукт называет неверный источник и выглядит уверенно. **Это прямое нарушение обещания «не выдумывать источник».**

#### Случай 2 — вероятностная атрибуция по своей природе

Шаг 3 назначает источник по времени. При нескольких кликах в окне ближайший не обязательно правильный. Логика это учитывает: уверенность снижается с дистанцией и при `eligibleClicks.length > 3` дополнительно падает на 0.1, минимум 0.2.

Это **осознанный компромисс, а не ошибка** — при условии, что уверенность честно показана в интерфейсе. Отсюда требование MVP: точное и расчётное всегда визуально различимы (S1-12, S1-23).

#### Чего система НЕ делает неправильно

Ранее была гипотеза, что запасная кампания в [attribution.service.ts:27](../../apps/api/src/attribution/attribution.service.ts#L27) может приписать органическую подписку случайной активной кампании. **Проверено по коду: не может.** `campaignId` в результате берётся из совпавшего клика или invite-ссылки, а запасная кампания влияет только на ширину окна (ошибка B).

### 3.4 Сценарии для проверки

| # | Сценарий | Ожидаем |
|---|---|---|
| U1 | Подписка по обычной t.me без клика | `ORGANIC`, не привязано к активной кампании |
| U2 | Клики в окне есть, invite не связан ни с одним | `UNKNOWN`, уверенность 0.10 |
| U3 | >50 кликов между целевым и подпиской | Должно быть `EXACT_CLICK_INVITE`; если стало `PROBABILISTIC` — ошибка A подтверждена |
| U4 | 5+ кликов в окне, ни одного точного | `PROBABILISTIC` с уверенностью ≤ 0.62 |
| U5 | Доля `UNKNOWN` в отчёте | Совпадает с `getAttributionStats()`, не прячется и не округляется в ноль |

## 7. Можно ли доверять данным сейчас

**В рабочем workspace — да, в пределах проверенного.** Баланс сходится, атрибуция назначается, ограничение снято, схема БД соответствует коду.

**Но три механизма не подтверждены практикой:**

| Механизм | Состояние |
|---|---|
| Resubscribe | Исправлен в коде и схеме, **ни одного цикла в данных** |
| «Дошёл до Telegram» | Исправлен вчера, **ни одного заполненного поля** |
| Отсев быстрых отписок | Выключен по умолчанию (`delay = 0`) |

Это не значит, что они сломаны. Это значит, что **утверждать их работоспособность оснований нет** — и продукт, который обещает честность данных, не должен обещать её на непроверенном.

Проверки 1–4 из раздела 6 закрывают этот пробел. Ни одна из них не требует написания нового функционала.
