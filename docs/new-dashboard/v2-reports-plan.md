## 1. Цель раздела

Продукт целиком отвечает на один вопрос: «откуда пришёл подписчик и можно ли доверять этим данным» ([`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md)). «Звіти» — раздел, где это доверие проверяется цифрами, а не декларируется.

Задача раздела конкретнее, чем «показать таблицы»:

> Пользователь смотрит в «Звіти» и получает не набор чисел, а решение: **какой источник работает, какой сжигает бюджет, и насколько уверенно это можно утверждать.**

Это прямо продолжение вопросов Q1, Q2, Q4, Q5 из [`MVP_SCOPE.md`](./MVP_SCOPE.md):

| # | Вопрос | Что закрывает «Звіти» |
|---|---|---|
| Q1 | Откуда пришёл подписчик? | Разрез «Джерела» + стрічка «Підписки» |
| Q2 | Какая реклама или источник работает? | Клики → дійшли → підписки → CR по джерелу |
| Q4 | Сколько ушло? | Стрічка «Відписки» с прив'язкою до джерела |
| Q5 | Можно ли доверять этим данным? | Блок «Якість даних» + честные состояния там, где данные не подтверждены |

**Раздел не обязан** заменять BI-систему, считать ROI/ROAS, объяснять аномалии текстом (S2-23 — Phase 2) или показывать разрезы по креативам/постам (Phase 2). Это сознательно узкий MVP: три источника правды (клики, підписки, відписки) в одном месте со сквозными фильтрами вместо шести разрозненных страниц.

## 2. Пользовательские сценарии

**Трафік-менеджер, отчитывается за рекламу**

```
запустив рекламу з UTM-міткою →
через кілька днів відкрив «Звіти → Джерела» →
побачив клики, частку тих, хто дійшов до Telegram, підписки, відписки, CR по кожному джерелу →
відключив джерело з низьким CR і високою часткою недійшлих, збільшив бюджет на сильне
```

Ключевое: без «частки дійшлих» менеджер винить канал за низький CR, хоча половина людей просто не долетає до Telegram (обоснование S2-12 в MVP_SCOPE.md).

**Власник каналу без агентства**

```
сам веде канал, роздав звичайне посилання t.me в шапці Instagram і в чужому чаті →
відкрив «Звіти» →
побачив, що велика частка підписок — «Джерело невідоме» / органіка →
зрозумів: скрізь, де можна, потрібно ставити трекінгову або invite-посилання, а не голий t.me
```

**Клієнт агентства, який не довіряє цифрам**

```
побачив у звіті просадку підписок →
відкрив «Якість даних» →
побачив, що частка «Ймовірне» чи «Невідомо» зросла →
зрозумів, що це питання якості розмітки, а не того, що агентство «малює» цифри →
за потреби провірив конкретну людину в «Учасниках»
```

**Власник, що перевіряє баланс**

```
відкрив «Звіти», обрав період →
побачив попередження, що сума по джерелах не збігається з приростом каналу →
зрозумів: цифрам за цей період довіряти не можна, поки не розібратись
```

(Сам банер балансу живе на «Огляд» — S1-25 — але фільтр періоду в «Звітах» мусить рахувати по тій самій логіці меж доби, інакше два екрани покажуть різні числа за нібито один період.)

## 3. Текущие API

Все ендпоінти вже існують у [`dashboard.controller.ts`](../../apps/api/src/dashboard/dashboard.controller.ts) / [`dashboard.service.ts`](../../apps/api/src/dashboard/dashboard.service.ts). Нового бекенду з нуля не потрібно — потрібні аддитивні правки (розділ 4).

| API | Назначение | Готовность |
|---|---|---|
| `GET /api/dashboard/overview` | Загальні показники, `attributions[]` (якість даних), `dataIntegrity` (баланс) | ⚠️ рахує за весь час, без `channelId` |
| `GET /api/dashboard/campaigns` | Розріз «Джерела»: клики, унікальні, підписки, відписки, CR по кампанії | ⚠️ без періоду/`channelId`; **баг** — відписки не скопійовані на кампанію (розділ 4) |
| `GET /api/dashboard/tracking-links` | Розріз «Посилання»: те саме по кожному tracking-посиланню | ⚠️ без періоду/`channelId`; N+1 (4 запити на посилання) |
| `GET /api/dashboard/subscribers` | Стрічка «Підписки» з джерелом і якістю атрибуції | ✅ фільтри `channelId/status/search/attributionType/limit` готові · ⚠️ без періоду |
| `GET /api/dashboard/unsubscribes` | Стрічка «Відписки» з джерелом (fallback-пошук профілю, якщо не прив'язаний напряму) | ✅ фільтри `channelId/search/limit` готові · ⚠️ без періоду |
| `overview → attributions[]` (`getAttributionStats()`) | «Якість даних»: частка EXACT/CAMPAIGN/PROBABILISTIC/ORGANIC/UNKNOWN + середня впевненість | ✅ готово як є |
| `GET /api/dashboard/subscribers/export.csv` | Експорт | ⚠️ лише список підписників, без BOM, фіксовані колонки, ігнорує фільтри/період |
| «Частка дійшлих до Telegram» (`ClickEvent.telegramOpenedAt`) | Потрібна для чесного CR (S2-12) | ❌ поле є й **підтверджено робочим** (розділ 6), агрегації немає ніде |
| `GET /api/dashboard/subscribers/:id` (`getSubscriberDossier`) | Картка людини — суміжний екран «Учасники», не «Звіти» | ✅ готово, поза межами цього документа |
| `GET /api/dashboard/bot-starts`, `pixel-delivery`, `daily-digest` | Воронка бота, доставка в рекламу, щоденний дайджест | Поза MVP «Звітів» — S2/S3, лишаються в старому кабінеті ([`REMOVED_FEATURES.md`](./REMOVED_FEATURES.md)) |

## 4. Требуемые backend изменения

Правило прежнее (MVP_TECHNICAL_PLAN.md, раздел 8): **только аддитивные изменения**. Ни одна существующая сигнатура не меняется — старый кабинет и уже реализованный `/v2/links`/`/v2/channels` не должны почувствовать разницу без новых параметров.

### Обязательно для MVP

1. **Исправить баг в `getCampaignReports()` — отписки считаются не по кампании, а по всему каналу.**

   [dashboard.service.ts:125-127](../../apps/api/src/dashboard/dashboard.service.ts#L125):

   ```ts
   this.prisma.unsubscribeEvent.count({
     where: { channelId: campaign.channelId },   // ← нет campaignId вообще
   }),
   ```

   Если на канале две активные кампании, у **обеих** строк «Джерела» будет одинаковое число отписок — суммарное по каналу, не имеющее отношения к конкретной кампании. Соседний метод [`getTrackingLinkReports()`](../../apps/api/src/dashboard/dashboard.service.ts#L184) уже решает это правильно — фильтрует через цепочку `subscriberProfile.membershipEvent.attribution.trackingLinkId`. Правка — скопировать тот же паттерн через `attribution.campaignId`. Это не новая логика, это починка существующей, до того как на неё будет опираться флагманский экран «Джерела». Без этой правки раздел нарушает главное правило продукта — не путать источник — на самой первой таблице, которую увидит пользователь.

2. **Период `?from=&to=`** — добавить как необязательные query-параметры к `getOverview`, `getCampaignReports`, `getTrackingLinkReports`, `getSubscriberFeed`, `getUnsubscribeFeed`. Без параметров поведение не меняется.

   Какое поле фильтруется в каждом случае:

   | Метод | Поле для `from/to` |
   |---|---|
   | `getOverview` | `ClickEvent.clickedAt` (клики), `MembershipEvent.occurredAt` (підписки/відписки) |
   | `getCampaignReports` / `getTrackingLinkReports` | `ClickEvent.clickedAt` для кліків, `attribution.membershipEvent.occurredAt` для підписок |
   | `getSubscriberFeed` | `SubscriberProfile.subscribedAt` |
   | `getUnsubscribeFeed` | `UnsubscribeEvent.occurredAt` |

   Границы суток считать в киевском времени, тем же способом, что уже есть в [`kyiv-time.ts`](../../packages/shared/src/kyiv-time.ts) (`kyivDayStart`) и `formatDateUk`. Это не произвольная осторожность — расхождение в 2–3 часа на границе суток уже было реальным багом и уже однажды чинилось ([MVP_TECHNICAL_PLAN.md](./MVP_TECHNICAL_PLAN.md), раздел 4.3). Наивный `new Date(from)` без учёта зоны повторит его на новом месте.

3. **Фильтр `?channelId=`** — уже есть в `getSubscriberFeed`/`getUnsubscribeFeed`, отсутствует в `getOverview`, `getCampaignReports`, `getTrackingLinkReports`. Нужен, потому что:
   - агентство ведёт несколько каналов в одном workspace (S2-01, уже мигрировано в «Канали»);
   - **глобального переключателя канала в шелле нет** — есть только `WorkspacePicker` ([Shell.tsx](../../apps/web/src/components/v2/Shell.tsx)), мокап с «[ Канал: Мій канал ▾ ]» из MVP_SCOPE.md ещё не реализован. «Звіти» не могут на него полагаться — фильтр канала должен быть собственным контролом на странице (паттерн выбора канала уже есть в конструкторе `/v2/links` — переиспользовать, а не изобретать).

4. **Агрегация `reached`** — `count(telegramOpenedAt IS NOT NULL)` рядом с `clicks` в `getOverview`, `getCampaignReports`, `getTrackingLinkReports`. Посчитать заодно `reachRate` на бэкенде (как уже сделано для `conversionRate`), чтобы фронтенд не изобретал свою формулу округления/деления на ноль на каждой странице отдельно.

### Можно позже

- Расширенные фильтры (по `utmSource`, по типу атрибуции в самом отчёте «Джерела», а не только в стрічке підписників).
- Сравнение с предыдущим периодом как отдельная backend-возможность — для MVP проще и дешевле сделать два вызова с фронта (текущий диапазон + предыдущий такой же длины), не усложняя контракт API.
- N+1 в `getTrackingLinkReports`/`getCampaignReports` (4 запроса на строку) — терпимо на текущих объёмах, зафиксировано как долг S5-07 в MVP_TECHNICAL_PLAN.md. Не блокирует MVP.
- `Campaign.isActive`-фильтр в `getCampaignReports` — сейчас безвреден (в коде нет ни одного места, которое переключает кампанию в `isActive: false` — проверено по `apps/api/src/campaign/`), но если архивирование кампаний появится в будущем, кампания молча исчезнет из «Джерела» вместе с историей. Не чинить сейчас, просто не забыть при добавлении архивации кампаний.
- Дополнительные метрики Phase 2: разрез по креативам (S2-19), по постам (S2-20), отписки по срокам (S2-21), мониторинг доли unknown (S1-26).

### ⚠️ Конфликт, требующий решения — экспорт

[`MVP_SCOPE.md`](./MVP_SCOPE.md) включает «Базовый экспорт» (S1-24) в критерии готовности MVP: *«Отчёт выгружается без потери кириллицы и меток»*. Бриф этой сессии прямым текстом относит экспорт к «НЕ делать сейчас». Это реальное расхождение между уже согласованным продуктовым документом и текущим брифом, а не то, что можно молча выбрать в одну сторону (правило 20, PROJECT_CONTEXT.md).

Предложение: отложить перестройку экспорта (BOM, произвольный отчёт вместо только `subscribers`) до отдельного захода, но явно зафиксировать это как сознательное отклонение от MVP_SCOPE.md в [`DECISIONS.md`](./DECISIONS.md), а не как тихо забытый пункт. Нужно подтверждение владельца продукта.

## 5. Структура интерфейса v2

Не шесть страниц старого кабинета (`/reports/overview`, `/sources`, `/subscriptions`, `/bot-starts` в меню + `/attribution-confidence`, `/pixel-delivery`, `/retention` вне меню, каждая почти без общих фильтров) — один раздел `/v2/reports` с состоянием фильтров в URL (`searchParams`), чтобы отчёт можно было сохранить в закладку и переслать.

```
┌─────────────────────────────────────────────────────────┐
│ Звіти                                                    │
│ Яке джерело працює, а яке спалює бюджет.                 │
├─────────────────────────────────────────────────────────┤
│ [ Період: 7 днів ▾ ]  [ Канал: усі ▾ ]     (стан фільтрів │
│                                              живе в URL)  │
├─────────────────────────────────────────────────────────┤
│  Джерела │ Посилання │ Підписки │ Відписки │ Якість даних│  ← секції/вкладки
├─────────────────────────────────────────────────────────┤
│                                                           │
│   (вміст активної вкладки)                               │
│                                                           │
└─────────────────────────────────────────────────────────┘
```

**Джерела** (типова вкладка за замовчуванням) — таблиця по кампаніях: назва, платформа, клики, **частка дійшлих до Telegram**, підписки, відписки, лишилось (нетто), CR клик→підписка. Клік по рядку — перехід у «Підписки» вже відфільтровані по цьому джерелу.

**Посилання** — та сама таблиця, розріз по `TrackingLink` замість `Campaign` (частина маркетологів ріже саме по посиланню/креативу, не по кампанії).

**Підписки** — стрічка з джерелом і бейджем якості атрибуції (той самий вигляд бейджа, що і в «Учасниках» — не винаходити нову палітру кольорів для тих самих п'яти типів атрибуції). Клік — перехід у картку підписника (`/v2/subscribers/:id`).

**Відписки** — стрічка з джерелом і часом у каналі. Показує, які джерела не просто приводять, а утримують.

**Якість даних** — не таблиця, а пояснювальний блок: частки EXACT_CLICK_INVITE / CAMPAIGN_INVITE / PROBABILISTIC / ORGANIC / UNKNOWN з короткими поясненнями, що означає кожен тип (переносимо текст з `attributionTypeLabel`, нове не вигадуємо). Контент старої `/reports/attribution-confidence` (не була в меню) переїжджає сюди повністю — окремого пункту не буде ([REMOVED_FEATURES.md](./REMOVED_FEATURES.md)).

**Новий компонент, якого зараз немає:** графік динаміки підписок/відписок по днях (лінійний/area chart). У [`components/v2/ui.tsx`](../../apps/web/src/components/v2/ui.tsx) графіків немає взагалі — тільки текстові/табличні стани. Коли дійде до коду, підключити skill `dataviz` до написання першого рядка графіка (кольори, форма, стани) — у цій сесії код не пишеться.

**Стани** (обов'язково для кожної вкладки, по прецеденту `/v2/links`):

| Стан | Коли | Приклад |
|---|---|---|
| `empty` | Дані є, але за обраний період/канал — порожньо | «За цей період кліків не було» + пропозиція розширити період |
| `loading` | `loading.tsx`, як у `/v2/links` | — |
| `error` | API не відповідає | Людський текст, технічний — в лог |
| `success` | Дані є | Таблиця/стрічка/графік |
| `disconnected` | Каналів ще немає взагалі | `DisconnectedState` → «Спочатку підключіть канал», лінк на «Канали» (той самий текст, що вже є в `/v2/links`) |

**Не переносити зі старого кабінету:** розбиття на окремі сторінки без спільних фільтрів, технічні назви полів у заголовках колонок, «сирий» банер балансу без пояснення (вже замінюється на «Огляд» — S1-25).

## 6. DATA TRUST ограничения

Проверено заново сегодня (2026-09-11), не только по документу вчерашнего дня — SQL-запросы к локальной БД и живой прогон QA-скрипта. Три риска из [`DATA_TRUST_CHECK.md`](./DATA_TRUST_CHECK.md) закрываются по-разному:

| Механизм | Вчера (2026-09-10) | Сегодня | Что это значит для «Звітів» |
|---|---|---|---|
| «Дійшов до Telegram» (`telegramOpenedAt`) | Полагались на код, живых подтверждений — 0 | **Подтверждено живим прогоном** `pnpm --filter @cleartg/api qa:smoke-tracking` → 8/8, включая `telegramOpenedAt` | Метрику reach можно строить — но см. оговорку ниже |
| Resubscribe (повторна підписка) | 0 циклів у даних | **Досі 0** — нового трафіку з учора не було (`max(clicked_at)` = 2026-09-09, до фіксу reach) | Код коректний, живою практикою не підтверджено. Не блокує розробку екрана, але «Підписки»/«Учасники» мусять бути готові показати два окремі цикли з різним джерелом — не тестовано наживо |
| Старе unique-обмеження на `subscriber_profiles` | 0 на локальній БД, staging/prod не перевірено | Те саме — **staging і production поза межами цієї сесії** (немає доступу/креденшлів) | Без цієї перевірки не можна на 100% довіряти `dataIntegrity.missing` на живих клієнтах |

Свіжий SQL (ідентичний вчорашньому — трафіку не було):

```
subscribe_without_attribution: 2  (ті самі тестові рядки verify-fix-* від 2026-07-24)

```

### Що саме дозволено показувати зараз

✅ **Можна.** Джерело кліку/підписки, типи атрибуції та впевненість (`EXACT_CLICK_INVITE` … `UNKNOWN`) — логіка перевірена по коду і даними, працює як задекларовано.

✅ **Можна, з важливою обмовкою.** Частка дійшлих до Telegram — фікс `4b53f4c` підтверджено живим кліком сьогодні. **Але:** всі 45 кліків у поточній базі — до фіксу, і `telegramOpenedAt = null` у них означає «поле ще не існувало», а не «людина не дійшла». Дані не дозволяють відрізнити один випадок від іншого заднім числом. **Показувати reach лише для періодів після 2026-09-10** (дати фіксу) або явно попереджати в інтерфейсі, що для більш раннього періоду метрика недостовірна технічно, а не тому що люди не доходили.

❌ **Не можна показувати, поки не полагоджено.** «Відписки» в розрізі «Джерела» — до виправлення бага з розділу 4 (п.1) число буде однаковим для всіх кампаній каналу. Показувати таку колонку — пряме порушення головного принципу продукту: не плутати джерело.

⚠️ **Показувати чесно, не ховати.** Частка `UNKNOWN`/`PROBABILISTIC` — це метрика якості, а не помилка (правило 9, PROJECT_CONTEXT.md). Не округляти до нуля, не ховати під нейтральним лейблом. Ризик «більше 50 кліків у вікні → втрата точної атрибуції» (Ошибка A з DATA_TRUST_CHECK.md) поки не проявився (максимум 28 у вікні), але не проявився — не означає «не станеться»: при масштабуванні трафіку вартий моніторингу, не переробки зараз.

⚠️ **Період.** Поки backend не рахує `from/to` (розділ 4, п.2), фільтр періоду в інтерфейсі не можна підключати до справжніх даних — або чесно писати «за весь час» замість підробленого «за 7 днів» над таблицею, яка насправді фільтр ігнорує.

## 7. План реализации

### Backend

1. Полагодити `getCampaignReports()` — відписки по `campaignId` через ланцюжок атрибуції, а не по всьому каналу (розділ 4, п.1). Найдешевший і найважливіший перший крок.
2. Додати `?from=&to=` до `getOverview`, `getCampaignReports`, `getTrackingLinkReports`, `getSubscriberFeed`, `getUnsubscribeFeed` — межі доби через `kyivDayStart`.
3. Додати `?channelId=` до `getOverview`, `getCampaignReports`, `getTrackingLinkReports`.
4. Додати `reached`/`reachRate` поруч з `clicks` у трьох методах, де рахуються кліки.
5. Не займати: `/l/:slug`, `/r/:slug`, `POST /telegram/webhook`, наявні сигнатури без нових параметрів.

### Frontend

1. `/v2/reports/page.tsx` — прибрати `ModulePlaceholder`, зібрати спільну панель фільтрів (період + канал), стан фільтрів у `searchParams`.
2. Нові компоненти в `components/v2/reports/`: таблиця джерел, таблиця посилань, стрічка підписок/відписок, блок якості даних, графік динаміки (новий тип компонента — раніше не було).
3. Перевикористати: `labels.ts` (`attributionTypeLabel`, `confidenceLabelUk`, `formatDateUk`, `sourceSummary`), стани з `ui.tsx`, патерн завантаження даних і обробки `AuthError` з `/v2/links/page.tsx`, вибір каналу — з конструктора посилань.
4. Один спільний варіант кольору/бейджа на п'ять типів атрибуції — визначити один раз, використовувати і в «Звітах», і в «Учасниках», не дублювати.
5. Deep-links: рядок джерела → відфільтрована стрічка підписок → картка людини в «Учасниках». Це і є «шар прийняття рішень», а не шість ізольованих сторінок.
6. Мобільна верстка — таблиці в `overflow-x`-контейнер або картки замість рядків на вузькому екрані; не повторювати борг, вже залишений в `/v2/links`.

### Testing

1. Юніт-тест на виправлення `getCampaignReports` — дві активні кампанії на каналі, відписка прив'язана лише до однієї, перевірити, що в звіті вона не потрапляє в другу.
2. Тест на «аддитивність»: виклик кожного зміненого ендпоінта без нових параметрів повертає те, що й раніше (правило з MVP_TECHNICAL_PLAN.md, розділ 7.3).
3. Тест на межу доби за Києвом для `from/to` (клік 23:59, підписка 00:01 — не повинні розʼїхатись по днях).
4. Розширити `qa:smoke-tracking` (або додати поруч такий самий скрипт, що сам за собою прибирає) перевіркою нової агрегації `reached`.
5. Живий прогін `/v2/reports` на реальних 45 кліках — звірити кожне число з прямим SQL-запитом, а не вважати роботою сам факт відображення таблиці (правило 18, PROJECT_CONTEXT.md).
6. Regression: старі `/reports/*` сторінки повертають те саме без нових query-параметрів; `pnpm --filter @cleartg/shared test` і `pnpm build:all` — зелені.
7. Поза цією сесією: перевірка старого unique-обмеження на staging/production (потрібен доступ, якого зараз немає) і живий прогін resubscribe-сценарію (R1–R4 з DATA_TRUST_CHECK.md) на реальному трафіку.

## Підсумок

1. **Розробку розділу «Звіти» можна починати** — після того, як закриті два пункти з розділу 4 («Обов'язково для MVP»), які є не побажанням, а передумовою чесних цифр: бекенд-баг у `getCampaignReports` і період/канал/reach.
2. **Backend-зміни потрібні, усі аддитивні:** виправлення бага з відписками по кампанії (найважливіше), `from/to`, `channelId`, агрегація `reached`. Жодна існуюча сигнатура не змінюється, нових таблиць і міграцій не потрібно.
3. **Ризики, які реально блокують чесний запуск:** (а) баг з відписками в «Джерелах» — блокує саме відкриття розділу з коректними цифрами; (б) відсутність фільтра періоду — без нього фільтр в інтерфейсі буде обманкою; (в) staging/production unique-обмеження й живий resubscribe-сценарій лишаються неперевіреними поза цією сесією — не блокують розробку екрана, але блокують повну впевненість у цифрах на реальних клієнтах.
4. **Що підтверджено і більше не є ризиком:** «дійшов до Telegram» — фікс `4b53f4c` перевірено живим прогоном сьогодні, 8/8. Це знімає один із трьох ризиків, зафіксованих учора в DATA_TRUST_CHECK.md.
5. **Метрики першої версії:** клики, частка дійшлих (з обмовкою про період до/після фіксу), підписки, відписки (після фіксу бага), нетто-приріст, CR клик→підписка, якість атрибуції (частки п'яти типів). Розрізи: по кампанії, по посиланню, стрічки підписок/відписок.
6. **На потім:** розширені фільтри, порівняння з попереднім періодом (робити на фронті двома викликами, не новим API), розріз по креативах/постах, відписки за термінами, моніторинг частки unknown, N+1-оптимізація, і — окремим рішенням власника — перебудова експорту (конфлікт із MVP_SCOPE.md, розділ 4).
