## 3. Главные продуктовые решения

### Тип ссылки

Пользователь **не выбирает** `SHORTLINK`, `LANDING_PAGE`, `LinkMode`, `/l/`, `/r/`.

Тип определяется системой из источника трафика. Фронтенд `linkMode` вообще не передаёт — бэкенд выводит его из платформы кампании ([link-mode.ts](../../packages/shared/src/link-mode.ts)).

Исключение: готовый адрес содержит `/l/` — его копируют в рекламный кабинет, спрятать нельзя.

### Кампании

Не отдельный раздел MVP. Создаются внутри конструктора ссылки через существующий `POST /api/campaigns`. Минимально: название + источник.

### Источники = кампании

В «Звітах» и на «Огляді» нет отдельных блоков «источники» и «кампании» — это один и тот же разрез (`getCampaignReports()` уже группирует по кампании).

### Список участников = циклы, не люди

`getSubscriberFeed()` отдаёт `SubscriberProfile` — один на цикл подписка → (отписка) → повторная подписка. Если у человека два цикла, в списке «Учасників» он встретится дважды строками с разными карточками. Это сознательно не группируется по человеку — каждая строка честно отражает реальное отдельное событие.

### «Пустое» состояние — не одно правило на весь кабинет

В «Звітах» пусто, когда `clicks === 0` (раздел целиком про рекламу — без кликов там нечего показывать). На «Огляді» это оказалось неверно: канал может расти органически без единого клика, и такую активность прятать нельзя — там условие `clicks === 0 && subscribers === 0` (оба должны быть нулевыми). Разница задокументирована в `V2_OVERVIEW_REVIEW.md` — это не расхождение по недосмотру, а разный охват двух разделов.

### Формулировка источника — единая там, где её пишет фронтенд

«Джерело не визначено» — канонический текст везде, где текст статический (пустые состояния, карточка учасника, рядок-звірка в «Звітах»). Сырые строки `joinSource` с бэкенда (списки, история циклов, лента активности) показываются как есть и туда не входят — это данные, не текст интерфейса, переписывать их на фронте значило бы расходиться с тем, что реально хранится. Подробности — `CORE_MVP_UX_REVIEW.md`.

### Удаление

Удаление ссылок и каналов **запрещено** в UI. Только два состояния: активная / архивная. Причина — `onDelete: Cascade` уничтожит историю кликов и атрибуции.

Для инвайтов — отзыв (необратим, Telegram перестаёт принимать вступление).

### Доступ к API

Мутации — только через **server actions**. Чтение — прямой серверный `fetch` через `lib/api.ts`. Клиентский `fetch` через прокси `/api/[...path]` возвращает 401: `JwtAuthGuard` читает только заголовок `Authorization`, а браузер шлёт cookie.

## 7. Следующий шаг

**Фронтенд и текст всех пяти разделов MVP готовы и запушены.** Три вещи остаются перед тем, как считать Core MVP закрытым официально — ни одна не требует нового модуля:

1. **Финальная проверка баланса** — MVP_SCOPE.md, раздел «Критерии готовности», прямо называет это «точкой невозврата»: «Сумма по всем источникам плюс unknown сходится с фактическим приростом канала». Технически показатель уже виден (`dataIntegrity.ok` на «Огляді» и «Звітах»), но отдельным явным шагом «весь MVP проверен на реальном канале от рекламы до отчёта» ещё не пройден.
2. **DATA TRUST, недоступное агенту** — unique-ограничение на staging/production и живой (не синтетический) resubscribe на реальном трафике. Требует либо доступа к другим базам, либо времени, за которое случится реальный повторный цикл подписки.
3. **Решения владельца, зафиксированные как предложения, не как готовые правки:** переименование «Учасники» → «Підписники»; конфликт по экспорту (MVP_SCOPE.md включает его в критерии готовности, брифы Reports/Subscribers — исключали каждый раз); редирект после входа по умолчанию на старый кабинет.

### Живая browser-проверка

`playwright` не входит в зависимости монорепозитория, но браузер (chromium) уже закеширован на машине (`~/Library/Caches/ms-playwright`). Для разового скрипта проверки: `npm install playwright --no-save` в любой временной директории (например, scratchpad), затем обычный node-скрипт с `require('playwright')`. Логин — тот же staging-флоу выше; кнопка входа делает клиентский `router.push`, а не полноценную навигацию — ждать нужно `page.waitForURL(...)`. Переключатель рабочего пространства в `WorkspacePicker` делает то же самое через `startTransition` — ждать нужно реального изменения значения `<select>`, а не просто `waitForLoadState`.

### Синтетические данные для живой проверки

Когда в реальном рабочем пространстве нужного сценария ещё не было (resubscribe, пустой workspace и т. п.) — самый надёжный способ: маленький Node-скрипт с `require('@cleartg/database')`, запущенный **из `apps/api/`** (там пакет резолвится нормально через node_modules; из произвольной внешней директории — нет).
