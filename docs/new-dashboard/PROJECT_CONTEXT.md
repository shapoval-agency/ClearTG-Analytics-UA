## 1. Что такое ClearTG

**ClearTG Analytics UA** — SaaS честной аналитики рекламы, которая ведёт людей в Telegram-каналы и Telegram-ботов.

Продукт отвечает на один главный вопрос:

> **Откуда пришёл каждый подписчик и насколько этим данным можно доверять.**

Вторая часть вопроса — «насколько можно доверять» — такая же важная, как первая. Продукт **не выдумывает источник**: если связь клика и подписки неоднозначна, подписка честно помечается как «источник не определён», а не приписывается ближайшей кампании. На этом строится доверие клиента к цифрам и вся ценность продукта.

Дальше данные возвращаются обратно в рекламные кабинеты (Meta, Google Ads, GA4, TikTok) как server-side конверсии, чтобы алгоритмы рекламы обучались на реальных подписках, а не на кликах.

---

## 2. Главная бизнес-задача

Цепочка ценности:

```
Реклама → клик → переход в Telegram → подписка → удержание
   ↑                                                  │
   └────── конверсия обратно в рекламный кабинет ──────┘
```

Что продукт обязан обеспечить:

1. **Зафиксировать** каждый клик со всеми рекламными метками (UTM, fbclid, gclid, ttclid).
2. **Связать** клик с конкретной подпиской в Telegram — точно, а не «на глаз».
3. **Показать** владельцу канала: сколько пришло, откуда, сколько осталось, где просадка.
4. **Вернуть** атрибутированную подписку в рекламный кабинет как конверсию.
5. **Честно сказать**, какая доля данных точная, какая расчётная, а какая — неизвестная.

## 3. Кто пользователь

**Основной пользователь — человек, который управляет каналом и/или закупает трафик.**

Два рабочих профиля:

| Профиль | Что делает | Что ему нужно от кабинета |
|---|---|---|
| **Владелец канала** | Ведёт свой Telegram-канал, покупает рекламу | «Сколько пришло, откуда, сколько осталось, где я теряю деньги» |
| **Агентство / трафик-менеджер** | Ведёт несколько клиентов и каналов, отвечает за закупку | Разрез по источникам/креативам/постам, выгрузка, отчёт клиенту |

Это **не разработчик и не инженер по данным**. Из этого следует главное правило языка интерфейса:

- ✅ говорим: источник, подписка, отписка, стоимость, качество данных, «дошёл до Telegram»
- ❌ не говорим в основном UI: `chat_member`, `invite_link`, `EXACT_CLICK_INVITE`, `webhook`, HTTP-коды

Технические термины допустимы только во второстепенных экранах диагностики.

## 4. Основные сущности

Это доменная модель продукта. Она **уже существует** в БД (`packages/database/prisma/schema.prisma`, ~30 моделей) и является общей для старого и нового кабинета.

### Ядро

| Сущность | Модель в БД | Смысл |
|---|---|---|
| **Рабочее пространство** | `Workspace`, `WorkspaceMember` | Клиент/проект. Всё скоупится по `workspaceId`. |
| **Канал** | `Channel` | Подключённый Telegram-канал. Ключ: `(workspaceId, telegramChatId)`. |
| **Кампания** | `Campaign` | Рекламная кампания: платформа, бюджет, окно атрибуции, целевое событие. |
| **Ссылка** | `TrackingLink` | Трекинговая ссылка сервиса: канал, режим, назначение, UTM, креатив, пост. |
| **Invite-ссылка** | `InviteLink` | Telegram invite. `PER_CLICK` — одноразовая под клик (точная атрибуция), `STANDALONE` — постоянная под источник (посев). |

### События

| Сущность | Модель в БД | Смысл |
|---|---|---|
| **Клик** | `ClickEvent` | Клик по ссылке + все рекламные идентификаторы + `telegramOpenedAt` («дошёл до Telegram»). |
| **Событие членства** | `MembershipEvent` | Подписка / отписка / одобрение заявки. Типы: `SUBSCRIBE`, `UNSUBSCRIBE`, `JOIN_REQUEST_APPROVED`, `JOIN_REQUEST_DECLINED`. |
| **Отписка** | `UnsubscribeEvent` | Отдельная запись, чтобы не терять исходную подписку. |
| **Старт бота** | `BotStartEvent` | `/start` в боте клиента. Уникален по `(botConnectionId, telegramUserId)`. |
| **Профиль подписчика** | `SubscriberProfile` | Досье: когда пришёл, откуда, retention D1/D7/D30. |

### Атрибуция и конверсии

| Сущность | Модель в БД | Смысл |
|---|---|---|
| **Атрибуция** | `Attribution` | Одна запись на `MembershipEvent`. Тип + `confidenceScore` + `reason`. |
| **Конверсия** | `ConversionEvent`, `ConversionDeliveryLog` | Событие, уходящее в рекламный кабинет, и лог доставки. |
| **Согласие** | `ConsentEvent` | Снимок согласия на момент клика. Гейтит отправку в рекламу. |

### Типы атрибуции (`AttributionType`)

От самого надёжного к самому слабому:

| Тип | Когда | Доверие |
|---|---|---|
| `EXACT_CLICK_INVITE` | Одноразовый invite, созданный под конкретный клик | Точное |
| `CAMPAIGN_INVITE` | Invite привязан к кампании/источнику | Высокое |
| `PROBABILISTIC` | Сопоставление по времени и доступным сигналам | Расчётное |
| `ORGANIC` | Подписка без рекламного клика | — |
| `UNKNOWN` | Источник определить нельзя | Не выдумываем |

**Правило:** `ORGANIC` и `UNKNOWN` — это результат, а не ошибка. Их доля — метрика качества данных, которую мы показываем клиенту, а не прячем.

## 5. Существующая архитектура

```
Monorepo (pnpm workspaces)
├── apps/api          — NestJS + Fastify, порт 3001: API, Telegram-бот, очереди
├── apps/web          — Next.js 15 (App Router) + React 19 + Tailwind, порт 3000
├── packages/database — Prisma schema (PostgreSQL), ~30 моделей
└── packages/shared   — чистые функции: атрибуция, consent, crypto, tracking, интеграции
                        (единственный код с полноценными unit-тестами)
```

### Фактический поток данных

```
Реклама (UTM + clickid в URL)
  → GET /l/:slug  или  /r/:slug          (tracking.controller.ts)
      → ClickEvent + ConsentEvent записаны
      → per-click invite (member_limit=1) через Bot API
      → 302 редирект в Telegram
  → человек подписывается вручную
  → Telegram webhook chat_member         (telegram.service.ts)
      → MembershipEvent + SubscriberProfile
      → AttributionService: 5-уровневый матчинг
      → ConversionEvent (PENDING / SKIPPED_*)
      → BullMQ 'conversion-delivery' → Meta / GA4 / Google Ads / TikTok
  → RetentionService (hourly cron): getChatMember → retainedD1/D7/D30
  → DashboardService → отчёты кабинета + ежедневный Telegram-дайджест (07:00)
```

### Ключевые точки

- **БД:** PostgreSQL через Prisma. Миграции — `prisma db push` (каталога `migrations/` нет).
- **Очереди:** Redis + BullMQ, три очереди: `conversion-delivery`, `retention-check`, `bot-daily-report`.
- **Telegram:** grammY. **Один глобальный админ-бот** (`TELEGRAM_BOT_TOKEN`) на всю платформу + отдельный рантайм клиентских ботов (`apps/api/src/client-bot`).
- **Авторизация:** magic link по email → JWT в httpOnly cookie. Фронт проксирует API через `/api/[...path]`.
- **Скоуп:** заголовок `x-workspace-id` для workspace-scoped endpoints.

## 7. Правила разработки

Эти правила зафиксированы в ТЗ (вкладка «AI — правила») и обязательны.

### Продукт

1. **Главный вопрос сервиса** — откуда пришёл подписчик и можно ли доверять этим данным. Функция, которая не помогает ответить на этот вопрос, требует отдельного обоснования.
2. **Каждая функция отвечает на вопрос «кому это нужно и какую проблему решает?»**. Нет ответа — функция не делается.

### Scope

3. **Не расширять задачу.** Реализуем только текущий ID из бэклога. Не добавляем «полезные» функции от себя.
4. **Не переходить на следующий этап**, пока текущий не работает как законченный слой.

### Архитектура

5. **Сначала изучить существующее.** До правок найти связанные модели, API, экраны, очереди и компоненты в старом кабинете.
6. **Не дублировать.** Если сущность/компонент уже есть — расширяем его, а не создаём параллельный.
7. **Не ломать старый кабинет.** Новый кабинет строится параллельно; старый остаётся рабочим, пока новый не заменит его функционально.

### Данные

8. **История сохраняется.** Переименование или изменение настроек ссылки/канала **не должно** уничтожать исторические события. Архивация вместо удаления.
9. **Не выдумывать источник.** Неоднозначный случай = `UNKNOWN`. Точные и расчётные данные всегда различимы в UI.
10. **Не создавать новые таблицы без необходимости** — см. раздел 8.

### Надёжность

11. **Аналитика не ломает трафик.** Отказ аналитики не должен мешать человеку попасть в Telegram. Fallback обязателен там, где он предусмотрен.
12. **Баланс событий должен сходиться.** Сумма по всем источникам + `unknown` = фактическое число подписок. Расхождение — это баг, а не «погрешность».

### UX

13. **Не плодить разделы.** Новая функция идёт в существующий логичный раздел без отдельного пункта меню, если это возможно.
14. **Состояния обязательны.** Для каждого интерфейса: `empty`, `loading`, `success`, `error`, `disconnected`.
15. **Сначала вывод, потом детали.** Кабинет помогает принять решение, а не просто показывает данные.
16. **Опасные действия объясняются до подтверждения** — что именно остановится и сохранится ли история. Пустой `confirm («Вы уверены?»)` запрещён.

### QA

17. **Агент тестирует сам.** После кода — happy path, ошибки, повторы, история, ключевые зависимости.
18. **UI не доказывает работу.** Подтверждаем событиями/данными/API, а не появлением кнопки.
19. **Не выдумывать результаты проверок.** Если команду нельзя запустить — сказать, что именно осталось непроверенным.

### Конфликты

20. **Не угадывать решение.** При конфликте требований — явно описать конфликт и остановить спорную часть, а не выбрать вариант молча.

## 8. Работа с базами данных

> **Критически важно: не создавать новые базы и таблицы без необходимости.**

Перед созданием любой новой таблицы обязательно проверить:

1. Есть ли уже такие данные в схеме?
2. Можно ли использовать существующую модель, добавив поле?
3. Можно ли сделать новый слой (view / сервис агрегации) поверх старой структуры?

**Схема уже покрывает больше, чем кажется.** Известные точки переиспользования:

| Задача | Что уже есть | Не создавать |
|---|---|---|
| Заявки на вступление в закрытый канал | `MembershipEventType.JOIN_REQUEST_APPROVED` / `JOIN_REQUEST_DECLINED` | Отдельную таблицу заявок |
| «Дошёл до Telegram» | `ClickEvent.telegramOpenedAt` | Отдельную таблицу reach-событий |
| Рассылки | `Mailing`, `MailingRecipient`, `MailingStatus` (модели есть, кода отправки нет) | Новые таблицы рассылок |
| API-доступ | `ApiKey` (модель есть, эндпоинтов нет) | Новую таблицу ключей |
| Свой бот клиента | `TelegramBotConnection`, `BotStartEvent` | Новые модели ботов |
| Лид-магниты | `LeadMagnet`, `LeadMagnetClaim` | Новые модели подарков |
| Сырые вебхуки | `WebhookEventRaw` | Новый лог вебхуков |
| Задержка конверсии, целевое событие | `Campaign.conversionDelayMinutes`, `Campaign.targetEvent` | Новые настройки конверсий |

**Осторожно с каскадами.** На `TrackingLink` стоит `onDelete: Cascade` для `ClickEvent`/`InviteLink`/`Attribution`. Удаление ссылки уносит с собой историческую аналитику. Правильный путь — архивация; при необходимости реального удаления сначала перевести связи на `SetNull`.

## 9. Ограничения

### Продуктовые и юридические

- Только **официальный Telegram Bot API**. Никакого userbot, MTProto-клиентов, парсинга.
- **Без российских интеграций и зависимостей.**
- **Сырой Telegram ID не передаётся в рекламные платформы** — только `externalIdHash`.
- Каждое внешнее событие имеет legal basis, consent status и лог доставки.
- Privacy by design: IP только в виде хеша, токены зашифрованы at rest (AES-256-GCM).

### Технические (известные, унаследованные)

Это фон, в котором мы работаем. Их не нужно чинить «заодно» — они разложены по этапам плана.

- Один глобальный админ-бот на всю платформу — единая точка отказа (задача S5-01).
- Нет retry/backoff/DLQ в очередях доставки конверсий (задача S3-04).
- Роль `VIEWER` не ограничивает запись на backend (задача S5-05).
- Нет rate limiting на публичных эндпоинтах (`/l/:slug`, `/api/auth/magic-link`, `/telegram/webhook`).
- `prisma db push` вместо `prisma migrate` — нет управляемой истории миграций.
- Небезопасные default-значения секретов (`ENCRYPTION_KEY`, `JWT_SECRET`, `HASH_SALT`) — нет fail-fast проверки на старте.
- Ноль тестов в `apps/api` и `apps/web` (есть только `packages/shared` + первый smoke-слой для tracking-ссылок от 2026-09-10).
- Нет CI-пайплайна с тестами.

### Запрещено без владельца продукта

- production-деплой;
- удаление или изменение реальных данных;
- изменение секретов;
- опасные миграции;
- изменение прав доступа;
- **прямые вызовы к продакшн Telegram-боту** (webhook/токен) — уже был инцидент со случайным `deleteWebhook()` на проде при локальном тесте.

## 10. Что не входит в продукт сейчас

- Биллинг (тарифы, LiqPay/WayForPay/Fondy) — оплата ручная.
- Telegram Mini App.
- Антифрод (фильтр дата-центров, VPN, headless).
- CRM/бот-конструкторы (SendPulse, KeyCRM, Make, n8n) — исследуется на этапе 04.
- Конструктор лендингов.
- Мультиязычность (UI на украинском, без переключателя языка).
