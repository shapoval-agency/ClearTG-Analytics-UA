# v2-subscribers-plan — раздел «Учасники»

> План перед кодом. Пятый и последний раздел MVP-навигации ([`MVP_SCOPE.md`](./MVP_SCOPE.md)). Backend не меняется — используются `getSubscriberFeed()` и `getSubscriberDossier()`, уже готовые и без изменений с прошлых этапов.

Дата: 2026-09-11

---

## 1. Цель раздела

Главная идея, данная в задаче: **«Я вижу конкретного подписчика и понимаю, откуда он пришёл».**

Проблема, которую решает раздел, — не учёт людей (это не CRM), а **проверка доверия к остальным разделам**. Когда клиент сомневается в цифрах «Звітів» («почему у меня 40% источник неизвестен — вы точно правильно считаете?»), самый дешёвый способ снять сомнение — открыть одного реального человека и увидеть: дата, источник, насколько система уверена в этом источнике. Это уже сформулировано в [`MVP_SCOPE.md`](./MVP_SCOPE.md), раздел «Учасники»: «когда клиент сомневается в отчёте, он проверяет одного человека».

Главный вопрос пользователя из брифа: **«Я вижу, что этот человек действительно пришёл из этого источника?»** — экран отвечает на него честно, включая случаи, когда источник неизвестен: раздел не имеет права выдумывать источник там, где система сама его не знает (то же правило, что уже применено в «Звітах» через строку «Джерело невідоме»).

## 2. Анализ текущего backend

### Модели

Задача называет модель «Subscriber» — такой модели в схеме нет. Реальная модель — **`SubscriberProfile`** ([schema.prisma:451](../../packages/database/prisma/schema.prisma#L451)): одна запись на один цикл «подписался → (возможно) отписался». У `MembershipEvent` и `Attribution` — общая структура с остальными разделами v2, ничего нового изучать не нужно, всё уже разобрано в [`v2-reports-plan.md`](./v2-reports-plan.md) и [`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md).

### API — оба метода готовы, backend не трогаем

| API | Метод | Что отдаёт |
|---|---|---|
| `GET /api/dashboard/subscribers` | `getSubscriberFeed()` | Список профилей с уже человеческими полями: `subscribedAt`, `isActive`, `joinSource` (готовая строка вида «Реклама: X /y» / «Джерело невідоме» / «Telegram напряму»), `attributionType`, `confidenceScore`, `campaignName`, `trackingLinkSlug`/`Name`, `channelTitle`. Фильтры уже приняты: `channelId`, `status` (`active`/`left`), `search` (по `telegramUserId` и `telegramUsername`), `attributionType`, `limit`, и — с прошлого этапа — `from`/`to` |
| `GET /api/dashboard/subscribers/:id` | `getSubscriberDossier()` | Одна карточка: канал, дата подписки, `isActive`, `daysInChannel`, атрибуция целиком (`type`, `confidence`, `reason`, `campaign`, `trackingLink`, `utm.*`, `creativeTag`, `postNumber`, `clickedAt`, `telegramOpenedAt`), ретеншн D1/D7/D30, флаги бота, лид-магниты, конверсии, и `unsubscribes` — но только для **этого самого** профиля |
| `GET /api/dashboard/subscribers/export.csv` | `exportSubscribersCsv()` | Готов, но в задаче явно исключён из этой итерации — не используем |

### Что можно показать

Всё, что нужно по брифу, уже есть в ответах без единого нового поля: дата подписки, статус, источник, кампания, ссылка (список); статус, дата, источник целиком, история (карточка).

### Важная находка — «история» не собирается одним вызовом

В проекте уже зафиксировано (тот же комментарий стоит в текущей заглушке `page.tsx` и в [`MVP_TECHNICAL_PLAN.md`](./MVP_TECHNICAL_PLAN.md), раздел 2.5): **у одного человека может быть несколько `SubscriberProfile` на один канал** — по одному на цикл подписка → отписка → повторная подписка. `getSubscriberDossier(id)` отдаёт **один** профиль, то есть один цикл, а не всю историю человека.

Бэкенд трогать нельзя (в задаче прямо запрещено), поэтому история собирается на фронтенде **из уже существующего** API: карточка дополнительно запрашивает `GET /api/dashboard/subscribers?search=<telegramUserId>&channelId=<channelId>&limit=50` и оставляет из результата только точные совпадения по `telegramUserId` (`search` ищет по вхождению подстроки, точное совпадение фильтруется на фронте). Из этого списка строится хронология циклов. Нового backend-кода это не требует — только второй вызов уже готового эндпоинта.

**Ограничение, о котором нужно сказать честно:** по данным [`DATA_TRUST_CHECK.md`](./DATA_TRUST_CHECK.md) на момент анализа в реальной базе **ни разу не было человека с двумя профилями** — цикл resubscribe в проде/локально не наблюдался ни разу. Интерфейс для истории из нескольких циклов будет готов, но проверить его можно только на одном профиле (типовой случай) — сценарий с реальным повторным циклом взять неоткуда.

### Что нельзя показывать

По правилам языка интерфейса ([`PROJECT_CONTEXT.md`](./PROJECT_CONTEXT.md), раздел 3) и прямому требованию брифа:

- внутренний `id` профиля (Prisma cuid) — используется только как ключ маршрута `/v2/subscribers/:id`, не как текст на экране;
- сырой `attributionType` (`EXACT_CLICK_INVITE` и т. п.) — только через `attributionTypeLabel()` из `lib/labels.ts`;
- `reason` атрибуции (английский технический текст типа `"Probabilistic match: nearest click 12 min before subscription"`) — диагностическое поле, не для основного экрана;
- ретеншн (D1/D7/D30), флаги бота, лид-магниты, конверсии — есть в ответе `getSubscriberDossier()`, но не входят в структуру карточки из брифа (Основная информация / Источник / История) — оставляем на будущее, не показываем сейчас, чтобы не расширять экран сверх заданного.

**Отдельно про точную формулировку.** Бриф прямо просит для неизвестного источника текст **«Джерело не визначено»**. Поле `joinSource`, которое уже отдаёт `getSubscriberFeed()`, в этом случае содержит немного другую строку — «Джерело невідоме» (тот же смысл, другое слово). На карточке используем ровно формулировку из брифа; в списке, где `joinSource` идёt как есть построчно, это не переименовываем — список показывает результат работы бекенда как есть, а карточка формулирует именно так, как попросили.

## 3. Пользовательский сценарий

**Проверка после сомнения в отчёте:**

```
открыл «Звіти», увидел высокую долю «Джерело невідоме» →
засомневался, что аналитика работает правильно →
открыл «Учасники» →
нашёл через поиск конкретного человека, о котором помнит, откуда он пришёл →
увидел источник на карточке и его совпадение с ожиданием →
доверие к остальным цифрам восстановлено (или найдена реальная проблема — тоже результат)
```

**Проверка нового подписчика сразу после запуска рекламы:**

```
запустил кампанию →
через день увидел первых подписчиков в «Звітах» →
открыл «Учасники», отсортировал по последним →
открыл карточку конкретного человека →
убедился, что источник — именно эта кампания, а не «Джерело невідоме»
```

**Проверка ушедшего подписчика:**

```
заметил в «Звітах» рост отписок →
открыл «Учасники», переключил статус на «Пішли» →
нашёл конкретного человека →
увидел, сколько дней он был в канале и откуда пришёл изначально
```
