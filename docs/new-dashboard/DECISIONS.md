# DECISIONS — журнал решений

> Здесь фиксируются важные решения по новому кабинету. Записанное решение агенты и разработчики **не переосмысливают** без нового согласования.

## Формат записи

```markdown
## DEC-NNN — краткое название

- **Дата:**
- **Решение:**
- **Почему:**
- **Что затрагивает:**
- **Кто подтвердил:**
```

Поле «Кто подтвердил» может быть:
- **Владелец продукта** — решение окончательное;
- **Предложено AI, ожидает подтверждения** — рабочая гипотеза, можно менять без пересогласования.

## DEC-001 — Новый кабинет строится параллельно старому

- **Дата:** 2026-09-10
- **Решение:** Старый кабинет не переписывается и не ломается. Новый кабинет разрабатывается параллельно и постепенно заменяет старый по мере готовности слоёв.
- **Почему:** Старый кабинет — работающий продукт с подключёнными базами и живыми клиентами. Одномоментная замена остановила бы сбор данных и аналитику у действующих пользователей.
- **Что затрагивает:** Весь процесс разработки. Любая задача проходит проверку «есть ли это в старом кабинете» перед реализацией.
- **Кто подтвердил:** Владелец продукта (постановка задачи от 2026-09-10)

## DEC-003 — Не создавать новые таблицы без проверки существующей схемы

- **Дата:** 2026-09-10
- **Решение:** Перед созданием любой новой таблицы проверить: есть ли уже такие данные, можно ли расширить существующую модель, можно ли сделать слой поверх старой структуры.
- **Почему:** Схема из ~30 моделей уже покрывает больше, чем кажется. Найденные точки переиспользования: `MembershipEventType.JOIN_REQUEST_APPROVED/DECLINED` (заявки в закрытый канал), `ClickEvent.telegramOpenedAt` (дошёл до Telegram), `Mailing`/`MailingRecipient` (рассылки), `ApiKey` (ключи API), `Campaign.conversionDelayMinutes` и `Campaign.targetEvent` (задержка конверсии и суперцели). Дублирующие таблицы разрушили бы целостность аналитики.
- **Что затрагивает:** `packages/database/prisma/schema.prisma`, задачи S2-14, S2-15, S3-09, S3-16, S4-07…S4-10, S4-13.
- **Кто подтвердил:** Владелец продукта (постановка задачи от 2026-09-10)

## DEC-004 — Разработка идёт строго по этапам

- **Дата:** 2026-09-10
- **Решение:** Этап 1 (Ядро) → 2 (Улучшение) → 3 (Реклама) → 4 (Автоматизация) → 5 (Масштабирование). Переход на следующий этап только после того, как текущий работает как законченный слой.
- **Почему:** Каждый следующий этап опирается на данные предыдущего. Рекламные интеграции без надёжной атрибуции отправляют мусор в рекламные кабинеты; автоматизация без работающих отчётов не имеет опоры.
- **Что затрагивает:** Порядок задач в [`NEW_DASHBOARD_PLAN.md`](./NEW_DASHBOARD_PLAN.md#4-порядок-разработки).
- **Кто подтвердил:** Владелец продукта (постановка задачи от 2026-09-10)

## DEC-005 — Навигация сокращается с 19 пунктов до 7 разделов

- **Дата:** 2026-09-10
- **Решение:** Плоское меню старого кабинета заменяется на 7 разделов: Огляд, Канали, Посилання, Звіти, Учасники, Інтеграції, Налаштування. Отдельные пункты «Кампанії», 4 рекламные интеграции и 4 страницы отчётов сворачиваются внутрь этих разделов.
- **Почему:** Правило ТЗ «не плодить разделы»: функция должна жить рядом с понятной пользователю сущностью, а не получать отдельный пункт меню. В старом кабинете 5 из 19 пунктов приходятся на одну сущность «Интеграции», а отчёты размазаны по 6 страницам, три из которых даже не попали в меню.
- **Что затрагивает:** [AppShell.tsx](../../apps/web/src/components/AppShell.tsx) (в старом кабинете не меняется), структура нового кабинета.
- **Кто подтвердил:** Предложено AI, ожидает подтверждения

## DEC-006 — LOCAL_MODE не переносится

- **Дата:** 2026-09-10
- **Решение:** Демо-режим на localStorage (`lib/local-mode.ts`, `lib/local-store.ts`, `hooks/useLocalData.ts`, `components/local/`) в новый кабинет не переносится.
- **Почему:** Это полностью изолированная эмуляция без backend, созданная для демонстрации на голом Vercel. По аудиту — «не имеет отношения к реальному функционалу». Фактически это вторая параллельная реализация тех же экранов, которую пришлось бы поддерживать дважды.
- **Что затрагивает:** [components/local/](../../apps/web/src/components/local/), [lib/local-mode.ts](../../apps/web/src/lib/local-mode.ts). В старом кабинете код остаётся нетронутым.
- **Кто подтвердил:** Предложено AI, ожидает подтверждения

## DEC-008 — Публичные маршруты трекинга и Telegram webhook защищены от изменений

- **Дата:** 2026-09-10
- **Решение:** `/l/:slug`, `/r/:slug`, `POST /telegram/webhook`, формат `externalIdHash` и имена полей в Prisma не меняются без явного согласования с владельцем продукта.
- **Почему:** URL трекинговых ссылок уже вшиты в запущенные рекламные кампании — их изменение делает трафик мёртвым. Webhook настроен на стороне Telegram, и уже был инцидент со случайным `deleteWebhook()` на проде. Смена соли или алгоритма хеширования обнулит сопоставление пользователей во всех рекламных кабинетах. Миграции идут через `prisma db push` без истории — откатить переименование нечем.
- **Что затрагивает:** [tracking.controller.ts](../../apps/api/src/tracking/tracking.controller.ts), [telegram.controller.ts](../../apps/api/src/telegram/telegram.controller.ts), [crypto.ts](../../packages/shared/src/crypto.ts), `schema.prisma`.
- **Кто подтвердил:** Предложено AI, ожидает подтверждения

## DEC-009 — MVP определяется пятью вопросами, а не готовностью кода

- **Дата:** 2026-09-10
- **Решение:** В первую версию нового кабинета попадают только функции, помогающие ответить на пять вопросов: откуда пришёл подписчик, какой источник работает, сколько пришло, сколько ушло, можно ли доверять данным. Наличие рабочего кода в старом кабинете не является основанием для включения в MVP.
- **Почему:** Иначе MVP превращается в перенос всего старого кабинета. Критерий успеха проекта — понятный продукт, который можно объяснить любому пользователю, а не максимальное число функций.
- **Что затрагивает:** [`PRODUCT_DECISION_MATRIX.md`](./PRODUCT_DECISION_MATRIX.md), [`MVP_SCOPE.md`](./MVP_SCOPE.md). Из 105 оценённых функций в MVP вошли 30.
- **Кто подтвердил:** Владелец продукта (постановка задачи от 2026-09-10)

## DEC-010 — Рекламные интеграции не входят в первую версию нового кабинета

- **Дата:** 2026-09-10
- **Решение:** Meta, Google Ads, GA4 и TikTok переносятся в PHASE 2. В период параллельной работы клиент управляет интеграциями в старом кабинете, где они продолжают работать.
- **Почему:** Отправка конверсий обратно в рекламу не входит в пять вопросов MVP и имеет смысл только на атрибуции, которой уже доверяют. Отправлять конверсии на непроверенной атрибуции — значит обучать рекламу на мусоре.
- **Что затрагивает:** Задачи S3-01 … S3-12, раздел «Інтеграції» в новом кабинете.
- **Кто подтвердил:** Предложено AI, ожидает подтверждения

## DEC-011 — Первая версия состоит из пяти разделов

- **Дата:** 2026-09-10
- **Решение:** MVP нового кабинета содержит разделы Огляд, Канали, Посилання, Звіти, Учасники. Разделы «Інтеграції» и «Налаштування» из полного плана появляются в PHASE 2.
- **Почему:** Пяти разделов достаточно, чтобы ответить на все пять вопросов. Раздел добавляется только тогда, когда внутри него есть работающая функция — пустых разделов «на будущее» не создаём.
- **Что затрагивает:** [`MVP_SCOPE.md`](./MVP_SCOPE.md). Уточняет DEC-005 применительно к первой версии.
