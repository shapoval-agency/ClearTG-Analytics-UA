## 1. Архитектура нового кабинета

### 1.1 Где живёт

Новый кабинет — **префикс маршрутов внутри существующего `apps/web`**, а не отдельное приложение.

```
apps/web/src/
├── app/
│   ├── v2/                    ← НОВЫЙ КАБИНЕТ
│   │   ├── layout.tsx         ← свой shell, своя навигация
│   │   ├── page.tsx           ← Огляд
│   │   ├── channels/
│   │   ├── links/
│   │   ├── reports/
│   │   └── subscribers/
│   ├── dashboard/             ← старый кабинет, не трогаем
│   ├── channels/              ← старый кабинет, не трогаем
│   └── ...                    ← остальные 20+ страниц старого кабинета
├── components/
│   ├── v2/                    ← НОВЫЕ компоненты
│   ├── AppShell.tsx           ← старый shell
│   └── ...
└── lib/                       ← ОБЩЕЕ: api, session, labels
```

**Почему не отдельное приложение `apps/web-v2`:** пришлось бы дублировать авторизацию, cookie-домен, API-прокси, middleware и конфигурацию Vercel. Аутентификация завязана на httpOnly-cookie конкретного домена — второй домен потребует отдельного входа.

**Единственное изменение в старом коде** — одна строка в [AppShell.tsx:32](../../apps/web/src/components/AppShell.tsx#L32): добавить `/v2` в массив `NO_SHELL`, чтобы старая боковая панель не оборачивала новый кабинет. Это тот же механизм, который уже используется для `/login` и `/onboarding` — идиоматично для существующего кода и обратимо.

> Альтернатива — перенести старые страницы в route-группу `(old)/`. Она чище, но требует перемещения 24 файлов. Отложено до момента, когда старый кабинет будет выключаться.

### 1.2 Технологии

Те же, что и в проекте. Новых зависимостей MVP не требует.

| Слой | Технология | Изменения для MVP |
|---|---|---|
| Frontend | Next.js 15 App Router, React 19, Tailwind | нет |
| Backend | NestJS + Fastify | только аддитивные query-параметры |
| БД | PostgreSQL + Prisma | **нет новых таблиц и полей** |
| Auth | JWT в httpOnly cookie | нет |

Оба кабинета читают **одну и ту же базу через один и тот же backend**. Пользователь может работать в обоих одновременно — данные не расходятся, потому что источник один.

Готовый TypeScript-контракт ответа — `DashboardOverview` в [lib/api.ts](../../apps/web/src/lib/api.ts#L48). Переиспользуем как есть.

**⚠️ Разрыв, который надо закрыть**

`getOverview(workspaceId)` **не принимает период** — считает за всё время. MVP требует показателей за период и сравнения с предыдущим ([S1-21](./PRODUCT_DECISION_MATRIX.md)). То же у `getCampaignReports()` и `getTrackingLinkReports()`.

Нужно: добавить необязательные `?from=&to=&channelId=` ко всем трём. Изменение **аддитивное** — без параметров поведение прежнее, старый кабинет не ломается.

**Компоненты (новые)**

| Компонент | Назначение |
|---|---|
| `KpiRow` | 4–6 показателей со сравнением периода |
| `TrendChart` | Динамика подписок и отписок |
| `SourceTopList` | Топ источников с долей, переход в «Звіти» |
| `DataQualityBlock` | Доля точных / расчётных / неизвестных |
| `BalanceBanner` | Расхождение баланса + объяснение, что делать |
| `CollectionStatus` | Канал отключён или бот потерял права |

> Существующий баннер в [dashboard/page.tsx:102](../../apps/web/src/app/dashboard/page.tsx#L102) показывает только техническую формулировку. В новом кабинете он должен объяснять причину и предлагать действие.

### 2.4 Звіти (`/v2/reports`)

Один раздел с общими фильтрами вместо шести страниц.

**Источники данных и расчёты**

| Разрез | API | Что считает | Готовность |
|---|---|---|---|
| Источники | `GET /api/dashboard/campaigns` | клики, уникальные, подписки, CR по кампании | ✅ |
| По ссылкам | `GET /api/dashboard/tracking-links` | клики, подписки, отписки, CR по ссылке | ✅ |
| Подписки | `GET /api/dashboard/subscribers` | лента с источником и качеством | ✅ фильтры есть |
| Отписки | `GET /api/dashboard/unsubscribes` | лента отписок | ✅ |
| Качество данных | `GET /api/dashboard/overview` → `attributions[]` | доля по типам атрибуции | ✅ |
| Экспорт | `GET /api/dashboard/subscribers/export.csv` | ⚠️ только подписчики | REBUILD |
| Доля дошедших | ❌ нет | ClickEvent где `telegramOpenedAt != null` | **NEW** |

**Три разрыва**

1. **Период.** Ни `getOverview`, ни `getCampaignReports`, ни `getTrackingLinkReports` не принимают диапазон дат. Нужны аддитивные `?from=&to=`.
2. **Доля дошедших до Telegram (S2-12).** Поле [ClickEvent.telegramOpenedAt](../../packages/database/prisma/schema.prisma#L328) заполняется (исправлено `4b53f4c`), но агрегации нет. Нужен `count(telegramOpenedAt != null)` рядом с `clicks` в отчётах — новых таблиц не требуется.
3. **Экспорт (S1-24).** Сейчас CSV есть только для подписчиков. Нужен общий экспорт текущего отчёта с UTF-8 BOM, чтобы Excel не ломал кириллицу.

**Производительность.** [getTrackingLinkReports()](../../apps/api/src/dashboard/dashboard.service.ts#L164) делает 4 запроса на каждую ссылку в цикле (N+1). На десятках ссылок терпимо, на сотнях — нет. Для MVP оставляем, помечаем как долг (S5-07).

## 4. Проверка существующей архитектуры

### 4.1 Backend

| Вопрос | Ответ |
|---|---|
| Существует ли API для всех функций MVP? | Да, кроме доли дошедших до Telegram |
| Подходит ли структура данных? | Да. `DashboardOverview` в [lib/api.ts:48](../../apps/web/src/lib/api.ts#L48) — готовый контракт |
| Есть ли ограничения? | Три, все обходятся аддитивно |

**Ограничение 1 — нет фильтра по периоду.** `getOverview`, `getCampaignReports`, `getTrackingLinkReports` считают за всё время.

## 6. DATA TRUST CHECK

> Отдельный аудит доверия к данным. **Проходится до того, как строятся отчёты**, потому что отчёт поверх неверных событий выглядит убедительно и врёт.

### 6.1 Проблема «залипания атрибуции при повторной подписке»

**Что это.** Человек подписался по рекламе A, отписался, подписался снова по рекламе B. Если система не создаёт новое событие, она продолжает показывать источник A. Агентство отчитывается неверными данными.

**Где проблема находилась (аудит от 2026-07-20, P0):**
- `@@unique([workspaceId, channelId, telegramUserId])` на `SubscriberProfile` — одна запись на человека
- ранний `return` в `processSubscribe` — повторная подписка не создавала событие

**Текущее состояние кода (проверено 2026-09-10):**

| Что | Где | Состояние |
|---|---|---|
| Уникальное ограничение | [schema.prisma:476-479](../../packages/database/prisma/schema.prisma#L476) | ✅ **снято**, явный комментарий: «одна людина може мати кілька профілів» |
| Дедупликация подписки | [telegram.service.ts:464](../../apps/api/src/telegram/telegram.service.ts#L464) | ✅ выходит только если у последнего профиля **нет** отписки |
| Создание нового профиля | [telegram.service.ts:489](../../apps/api/src/telegram/telegram.service.ts#L489) | ✅ новый профиль на каждый цикл |
| Дедупликация отписки | [telegram.service.ts:541](../../apps/api/src/telegram/telegram.service.ts#L541) | ✅ привязана к профилю, а не к 60-секундному окну (`e0a3cb8`) |

**Вывод: в коде исправление есть.**

### 6.2 Главный остаточный риск

> **Код исправлен, но база может быть не обновлена — и провал происходит молча.**

[telegram.service.ts:503-508](../../apps/api/src/telegram/telegram.service.ts#L503) (лог — строка 505):

```
catch (P2002) → залогировать → return
```

Если в конкретной базе **старое уникальное ограничение ещё существует** (миграции идут через `prisma db push` без истории — раздел 4.2), то:

1. `subscriberProfile.create` падает с `P2002`
2. обработчик выходит **до** `attributeMembership()` и `createSubscribeEvent()`
3. `MembershipEvent` остаётся **без атрибуции**
4. в интерфейсе это видно только как рост `dataIntegrity.missing`

Ошибка не всплывает в UI и не ломает процесс — она тихо теряет атрибуцию.

**Как подтвердить, что база в порядке:**

```sql
-- Должно вернуть 0 строк. Любая строка = старое ограничение живо.
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'subscriber_profiles'
  AND indexdef LIKE '%UNIQUE%'
  AND indexdef LIKE '%telegram_user_id%';
```

Дополнительно — поиск в логах API строки `subscriberProfile.create P2002`. Хотя бы одно вхождение означает, что атрибуция терялась.

**Проверить на каждой базе:** локальной, staging и продакшн. Это разные инстансы с разной историей `db push`.

### 6.3 Обязательные проверки

| # | Что проверяем | Как | Ожидаем |
|---|---|---|---|
| 1 | **Корректность подписок** | Подписаться по трекинговой ссылке | 1 `MembershipEvent`, 1 `SubscriberProfile`, 1 `Attribution` типа `EXACT_CLICK_INVITE` |
| 2 | **Дубликаты подписки** | Telegram шлёт несколько `chat_member` подряд | Второй не создаёт профиль |
| 3 | **Корректность отписок** | Отписаться | `UnsubscribeEvent` привязан к активному профилю; исходная подписка **не удалена** |
| 4 | **Повторная подписка** | Подписка A → отписка → подписка B (другая ссылка) | 2 профиля, 2 атрибуции, **разные `trackingLinkId`** |
| 5 | **Смена источника** | То же, что 4 | Второй профиль показывает B, первый остаётся с A |
| 6 | **Быстрые циклы** | 3 цикла подписка → отписка за минуту | 3 профиля и 3 отписки, не схлопнуты (регрессия `e0a3cb8`) |
| 7 | **Unknown честный** | Подписка по обычной t.me без клика | `ORGANIC` или `UNKNOWN`, **не** приписано активной кампании |
| 8 | **Баланс событий** | `GET /api/dashboard/overview` | `attributed === subscribers`, `missing === 0` |
| 9 | **Пропущенная отписка** | Подписка → отписка не записана → новая подписка | ⚠️ см. 6.4 |
| 10 | **Много кликов в окне** | >50 кликов между кликом и подпиской | ⚠️ см. 6.4 |

### 6.4 Два риска, найденных при чтении кода

Оба требуют проверки — статическим анализом подтвердить нельзя.

**Риск A — потеря точной атрибуции при большом объёме кликов**

[attribution.service.ts:41](../../apps/api/src/attribution/attribution.service.ts#L41) выбирает `take: 50` последних кликов в окне. Затем [attribution.ts](../../packages/shared/src/attribution.ts) шаг 1 ищет среди них клик по `inviteLinkUsed.clickEventId`.

Если исходный клик человека **не попал в эти 50** (окно по умолчанию 7 дней, за это время на активном канале кликов больше), поиск не находит его. Шаг 2b требует `!clickEventId` и тоже не срабатывает. Логика доходит до шага 3 и приписывает подписку **ближайшему чужому клику** как `PROBABILISTIC`.

Это не понижение уверенности, а **назначение неверного источника**.

Проверка: создать >50 кликов между целевым кликом и подпиской, убедиться, что атрибуция осталась `EXACT_CLICK_INVITE`.

**Риск B — окно атрибуции зависит от произвольной кампании**

[attribution.service.ts:27-32](../../apps/api/src/attribution/attribution.service.ts#L27): если у invite-ссылки нет кампании, берётся `findFirst({ channelId, isActive: true }, orderBy: createdAt desc)` — **последняя созданная активная кампания канала**.

При нескольких активных кампаниях с разными окнами результат зависит от того, какая создана последней. На сам источник это не влияет (`campaignId` в результате берётся из клика), но влияет на **ширину окна**, а значит на то, попадёт клик в атрибуцию или нет.

Проверка: две активные кампании с окнами 1 час и 7 дней, подписка через 3 часа после клика — убедиться, что результат объясним и стабилен.

### 6.5 Замечание по проверке баланса

[dashboard.service.ts:42-47](../../apps/api/src/dashboard/dashboard.service.ts#L42):

```
missing: Math.max(0, subscribers - attributedCount)
ok: attributedCount >= subscribers
```

Проверка односторонняя — ловит недостачу атрибуций, но не расхождение в другую сторону. Структурно перекос вверх невозможен (`Attribution.membershipEventId` уникален и каскадно удаляется), поэтому это не баг. Но инвариант — **равенство**, и в тесте утверждать надо именно `===`, а не `>=`.

## 7. Тестирование MVP

### 7.1 Happy path

**Сквозной сценарий — главный тест релиза:**

```
1. Пользователь входит по magic link
2. Подключает канал, бот получает права  → статус «работает»
3. Создаёт трекинговую ссылку с UTM и креативом
4. Переходит по ссылке                    → ClickEvent записан
5. Попадает в Telegram                    → telegramOpenedAt заполнен
6. Подписывается на канал                 → MembershipEvent + SubscriberProfile
7. Открывает Огляд                        → подписка видна, баланс сходится
8. Открывает Звіти → Джерела              → источник виден с типом атрибуции
9. Открывает карточку подписчика          → тот же источник
10. Выгружает отчёт                       → кириллица не сломана
```

**По модулям**

| Модуль | Happy path |
|---|---|
| Канали | Подключил → увидел «работает» → архивировал → восстановил, история цела |
| Посилання | Создал три типа ссылок → каждая ведёт куда обещано |
| Звіти | Выбрал период и канал → цифры изменились согласованно |
| Учасники | Нашёл человека поиском → увидел источник и историю |
| Огляд | Открыл → за 10 секунд понял, есть ли проблема |

| **Создавать дублирующие модели** | Схема покрывает все 30 функций MVP. Новых таблиц и полей не требуется |
| **Переносить весь старый кабинет** | В MVP входит 30 функций из 105. Остальные остаются в старом кабинете |
| **Добавлять функции вне MVP** | Список закрыт в [MVP_SCOPE.md](./MVP_SCOPE.md). Расширение — только через [DECISIONS.md](./DECISIONS.md) |
| **Менять бизнес-логику без решения** | Логика атрибуции, окна, уровни доверия — только с записью в журнал решений |

| Что | Путь | Почему |
|---|---|---|

### 4. Риски, блокирующие запуск

| # | Риск | Почему блокирует | Что делать |
|---|---|---|---|
| 1 | **Старое unique-ограничение живо в базе** | Атрибуция теряется молча, баланс не сойдётся | SQL-проверка на всех трёх базах — раздел 6.2. **Делать первым** |
| 2 | **Потеря точной атрибуции при >50 кликов в окне** | Подписка приписывается чужому клику. Прямая ложь клиенту | Проверить риск A, при подтверждении — исправить выборку |
| 3 | **Резабскрайб не перепроверен после `e0a3cb8`** | Вернувшийся подписчик может показывать старый источник | Сценарии 4, 5, 6 из раздела 6.3 |
| 4 | **Нет тестов на подписку и отписку** | Регрессия в ядре не будет замечена | Создать тесты `processSubscribe` |
| 5 | **Окно атрибуции от произвольной кампании** | При нескольких кампаниях результат плохо объясним | Проверить риск B |
| 6 | **Не решены вопросы владельца** | Q6 закрытые каналы, Q7 скрипт — меняют состав MVP | [DECISIONS.md](./DECISIONS.md) |

> Риски 1–3 — про доверие к данным. Если хоть один подтвердится, релиз откладывается: продукт, который врёт об источнике, хуже, чем отсутствие продукта.

### 5. Рекомендуемый порядок действий

```
1.  SQL-проверка unique-ограничения на трёх базах        ← 30 минут, делать первым
2.  Тесты processSubscribe: сценарии 4, 6, 9
3.  Проверка рисков A и B
    │
    ├─ подтвердились → исправить, вернуться к шагу 2
    └─ чисто → дальше
    │
4.  Ответы владельца на Q6 и Q7                          ← фиксирует состав MVP
5.  Этап 0: каркас (6 задач)
6.  Каналы → Ссылки                                      ← без них нет данных
7.  Backend: период + доля дошедших                      ← аддитивно
8.  Отчёты → Огляд → Учасники
9.  Экспорт
10. Regression: старый кабинет цел
11. Сквозной happy path на реальном канале
12. Финальная проверка баланса событий                   ← точка невозврата
```

**Шаги 1–3 не про новый кабинет — они про то, можно ли доверять данным, на которых он будет построен.** Начинать интерфейс раньше означает строить отчёты поверх неподтверждённого фундамента.

---

**Главный принцип:** не копия старого кабинета, а новый понятный продукт поверх проверенной бизнес-логики. Backend уже проверен работой — переписывать его не нужно. Работа MVP в том, чтобы честно показать то, что он уже умеет считать.
