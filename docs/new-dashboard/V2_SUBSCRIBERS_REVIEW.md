# V2_SUBSCRIBERS_REVIEW — отчёт о реализации `/v2/subscribers`

> По плану [`v2-subscribers-plan.md`](./v2-subscribers-plan.md). Backend не менялся — используются `getSubscriberFeed()` и `getSubscriberDossier()` как есть.

Дата: 2026-09-11

---

## Реализовано

**Список** `/v2/subscribers`: дата подписки, статус, источник (`joinSource` из бэкенда как есть), кампания (если есть), ссылка (если есть), плюс канал — без технических полей (внутренний `id` — только ключ ссылки, не текст на экране). Фильтры — только поиск и статус, оба в URL, ничего сверх брифа.

**Карточка** `/v2/subscribers/[id]`: три блока строго по структуре брифа.

- **Основная информация** — участник (`@username` или `ID <telegram id>`, если username не задан), канал, статус, дата подписки, для отписавшихся — дата отписки и сколько дней пробыл.
- **Источник** — если атрибуция уверенная (реклама с кампанией или ссылкой): тип, уверенность (словом и в процентах), кампания, ссылка. Если `ORGANIC`: честная фраза про прямой вступ без рекламы (это не то же самое, что «неизвестно», — система знает, что это не реклама). Если источник не определён — ровно фраза из брифа: **«Джерело не визначено»**. Не гадаем.
- **История** — список циклов «подписка → (отписка) → повторная подписка» для этого человека на этом канале. Собирается на странице вторым вызовом уже существующего `GET /api/dashboard/subscribers?search=` (см. «Использованные API») — нового backend-метода нет.

Пять состояний: `loading`, `disconnected` (нет каналов), два вида `empty` (участников вообще ещё не было / по текущему поиску и фильтру никого не нашлось), `error` (сервис/сессия/404 на карточке), `success`.

## Использованные API

| Запрос | Где | Назначение |
|---|---|---|
| `GET /api/channels` | список | Только для проверки «есть ли подключённые каналы» (состояние `disconnected`) |
| `GET /api/dashboard/subscribers?search=&status=` | список | Строки таблицы. `channelId`/`from`/`to` бэкенд уже принимает, но в фильтры интерфейса не выведены — бриф прямо просит оставить только поиск и статус |
| `GET /api/dashboard/subscribers/:id` | карточка | Один профиль — один цикл подписки |
| `GET /api/dashboard/subscribers?search=<telegramUserId>&channelId=` | карточка, блок «История» | Тот же список-эндпоинт, второй раз — находит все профили этого человека на этом канале. Результат фильтруется на фронте по точному совпадению `telegramUserId` (сам запрос ищет по вхождению подстроки) |

Ни одного нового backend-метода, поля или параметра — все три запроса существовали до этой задачи.

## Проверенные сценарии

Все проверки — на реальном рабочем пространстве «Кабінет клієнта (demo)» через staging-логин, плюс пять синтетических профилей, добавленных и удалённых прямо для этой проверки (см. «Ограничения» — в реальных данных на момент проверки существовал только один подписчик и ни одного цикла resubscribe).

| # | Сценарий | Как проверено | Результат |
|---|---|---|---|
| 1 | Есть подписчик с атрибуцией | Реальный подписчик `@Golofaev_Alex`: `PROBABILISTIC`, ссылка «meta test», без кампании | Карточка показала тип, уверенность **62% · середня**, ссылку по имени (не по служебному slug — см. «Ограничения») |
| 2 | Есть подписчик без источника | Синтетический профиль с `UNKNOWN`, без username | Показано ровно **«Джерело не визначено»**; в списке и в карточке — `ID <telegram id>` вместо `@username` |
| 3 | Нет участников | Проверено логикой два раза: пустой поиск/фильтр на реальных данных (не пусто, участник есть) — используем неглавный сценарий отдельно: поиск с заведомо несуществующим текстом → «Нікого не знайдено» | Подтверждено live-скриншотом; отдельный экран «участников вообще нет» не наблюдался вживую (в рабочем пространстве всегда есть хотя бы один канал с историей) — код идентичен уже проверенному в `/v2/reports` |
| 4 | Есть несколько участников | Список с 6 строками (1 реальный + 5 синтетических), фильтр `status=active` → 4 строки, `status=left` → 2 строки — числа сошлись точно | Подтверждено |
| (доп.) | Повторная подписка (resubscribe) | Синтетический человек с двумя профилями на одном канале: цикл 1 — `CAMPAIGN_INVITE`, отписался; цикл 2 — `PROBABILISTIC`, активен | Карточка показала **оба** цикла, с разными источниками у каждого, текущий подсвечен — впервые в этом проекте живьём подтверждён сценарий, для которого в реальных данных пока не было ни одного примера |

Дополнительно: `ORGANIC` (прямой вступ) — показана честная фраза без слова «невідоме»; карточка с несуществующим `id` — «Учасника не знайдено», а не падение страницы; полный обход всех страниц старого и нового кабинета (32 маршрута, включая новые `/v2/subscribers` и `/v2/subscribers/:id`) — все 200, 0 ошибок консоли.

Все синтетические профили и их события удалены сразу после проверки — реальный подписчик и счётчики базы не изменились.

## Ограничения

- **Дублирование строк для одного человека в списке.** `getSubscriberFeed()` отдаёт профили (циклы), не людей: если у человека два профиля, в списке он встретится дважды, с двумя разными карточками. Это не ошибка, а прямое следствие модели данных (`SubscriberProfile` = один цикл), и группировка по человеку в списке не делалась намеренно — бриф просит не добавлять сложную логику, а данные и так честны: каждая строка — реальное отдельное событие.
- **Точная дата отписки в «Истории» есть только для текущего профиля.** Для соседних циклов список показывает дату подписки, статус и источник (из `GET /api/dashboard/subscribers`, где даты отписки нет), а не точный момент ухода — его пришлось бы доставать отдельным вызовом досье на каждый цикл, что не оправдано для сценария, который на реальных данных проекта пока не наблюдался ни разу.
- **Название ссылки в блоке «Источник» — обходной путь, не факт бэкенда.** `getSubscriberDossier()` отдаёt для ссылки только `slug`, не имя (`getSubscriberFeed()`, наоборот, отдаёт оба поля). Карточка достаёт имя из уже загруженного списка истории; если этот второй запрос не удался, останется slug — корректно, просто менее по-человечески.
- **Не показано:** ретеншн D1/D7/D30, флаги бота, лид-магниты, конверсии — всё это есть в ответе `getSubscriberDossier()`, но не входит в структуру карточки из брифа (Основная информация / Источник / История).
- **Экспорт не подключён**, хотя `GET /api/dashboard/subscribers/export.csv` готов — бриф явно исключает экспорт из этой итерации.
- **Пагинации нет** — `getSubscriberFeed()` отдаёт до `limit` (по умолчанию 100) без курсора, тот же долг, что уже отмечен для `/v2/links` и `/v2/reports`.

## Что оставить на будущее

| Что | Комментарий |
|---|---|
| Группировка списка по человеку, а не по циклу | Требует продуктового решения — сейчас каждая строка это честное отдельное событие |
| Точная дата отписки для всех циклов истории, не только текущего | Нужен либо отдельный вызов на цикл, либо доработка `getSubscriberFeed()` |
| Имя ссылки напрямую в `getSubscriberDossier()` | Аддитивное расширение ответа (сейчас — только slug), backend в этой задаче не трогали |
| Ретеншн, лид-магниты, конверсии на карточке | Не входит в MVP-структуру карточки, данные уже есть в API |
| Экспорт списка участников | Явно исключено брифом этой задачи |
| Пагинация | Общий долг с остальными списками v2 |
