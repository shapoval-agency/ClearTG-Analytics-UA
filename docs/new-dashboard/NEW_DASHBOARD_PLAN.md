# NEW_DASHBOARD_PLAN — план нового кабинета

> Новый кабинет строится **параллельно** старому и постепенно его заменяет.
> Не копируем весь старый интерфейс. Переносим только то, что отвечает на вопрос «кому это нужно и какую проблему решает?».

Основано на `ClearTG_переработанное_ТЗ_v1.xlsx` (вкладки «01 Ядро» … «05 Масштабирование», «AI — дизайн», «AI — правила»).

---

## 1. Принципы интерфейса

Из вкладки «AI — дизайн». Это критерии приёмки любого экрана, а не пожелания.

| Правило | Делать | Не делать |
|---|---|---|
| **Цель кабинета** | Сначала состояние и вывод, затем детали и действие | Десятки KPI-карточек и таблицы без вывода |
| **Язык** | Источник, подписка, стоимость, отписка, качество | `chat_member`, `invite_link`, HTTP-коды в основном UI |
| **Навигация** | Функция живёт рядом с понятной пользователю сущностью | Отдельный пункт меню под каждый переключатель |
| **Главный экран** | За 10 секунд ответить: что произошло и есть ли проблема | Полный набор таблиц и настроек на первом экране |
| **Таблицы** | Фильтры, сортировка, поиск; детали открываются по строке | 20 колонок одновременно |
| **Статусы** | Работает / Требует внимания / Отключено + действие | Сырые ошибки API без объяснения |
| **Опасные действия** | Объяснить, что остановится и сохранится ли история | Пустой `confirm («Вы уверены?»)` |
| **Mobile** | Перестраивать карточки и списки; действия без hover | Ужатая desktop-таблица |
| **Progressive disclosure** | Простой базовый экран, advanced — вторым уровнем | Все возможности сразу |
| **Состояния** | `empty`, `loading`, `error`, `success`, `disconnected` для каждого экрана | Экран, спроектированный только для happy path |

### 2.1 Огляд

**Задача:** за 10 секунд ответить — что произошло и есть ли проблема.

| Блок | Содержание | Задачи |
|---|---|---|
| Ключевые показатели | 4–6 штук: пришло / ушло / осталось / стоимость / качество данных. Сравнение с прошлым периодом | S1-21 |
| Источники | Топ источников с долей и динамикой, переход в «Звіти» | S1-22 |
| Качество данных | Доля точных / расчётных / неизвестных + баланс событий | S1-23, S1-25 |
| Заметные изменения | Просадка источника, рост отписок, рост unknown | S2-23, S1-26 |

> Не выносить на главный экран: полные таблицы, настройки, технические логи.

### 2.2 Канали

| Блок | Содержание | Задачи |

| Подключение | Добавление канала, проверка прав бота, понятная ошибка | S1-01, S1-02 |
| Состояние интеграции | Канал + сбор + реклама + скрипт + режимы на одном экране | S2-16 |
| Диагностика | Кнопка «Проверить» → отчёт по скрипту, ссылкам, доступам | S2-17 |

| Доступ | Автоприём заявок для закрытых каналов | S2-14 |
| Отключение | Явный статус при потере прав, восстановление с сохранением истории | S1-05 |

### 2.3 Посилання

**Задача:** создать ссылку под конкретный источник и не потерять историю при изменениях.

| Блок | Содержание | Задачи |
|---|---|---|
| Конструктор | Канал → тип → пост → метки → готовая ссылка | S1-19 |
| Типы ссылок | Обычная (`unknown`), invite с источником, трекинговая, в бота, в личку | S1-06, S1-07, S1-08, S2-03, S2-05 |
| Разметка | UTM + метка креатива + посадочный пост | S1-13, S1-14 |
| Список | Название, канал, тип, метки, статус | S1-20 |
| Операции | Дублировать, редактировать без потери истории, архивировать | S2-06, S2-07, S2-08 |
| Массовое создание | Пачка ссылок под кампанию одной операцией | S2-09 |

> **Кампании не отдельный раздел.** Кампания — это свойство ссылки (группировка) и разрез в отчётах. Экран `/campaigns` из старого кабинета не переносится как пункт меню.

## 4. Порядок разработки

Работаем строго по этапам. **Не переходим дальше, пока текущий слой не работает стабильно.**

### Этап 1 — Ядро продукта (26 задач)

> Первая рабочая версия: сбор событий → атрибуция → ссылки и метки → базовые отчёты.

Порядок внутри этапа задан зависимостями:

```
1. Каналы и события     S1-01 → S1-02 → S1-03 → S1-04 → S1-05
2. Ссылки               S1-06, S1-07, S1-08 → S1-13, S1-14 → S1-19 → S1-20
3. Скрипт лендинга      S1-15 → S1-16 → S1-17 → S1-18
4. Атрибуция            S1-09, S1-10 → S1-11 → S1-12
5. Отчёты               S1-21, S1-22 → S1-23 → S1-24
6. Контроль данных      S1-25 → S1-26
```

**Критерий готовности этапа:** сумма подписок по всем источникам плюс `unknown` сходится с фактическим приростом канала, и это видно в кабинете.

### Этап 2 — Улучшение (25 задач)

> Дополнительные сценарии, UX, качество трафика, закрытые каналы.

```
1. Несколько каналов и боты   S2-01 → S2-02 → S2-03 → S2-04, S2-05
2. Работа со ссылками         S2-06, S2-07, S2-08 → S2-09
3. Качество трафика           S2-10 → S2-11, S2-12 → S2-13
4. Закрытые каналы            S2-14 → S2-15
5. Настройки и диагностика    S2-16 → S2-17 → S2-18
6. Отчёты и подписчики        S2-19, S2-20, S2-21, S2-22 → S2-23

**Критерий готовности:** видно, какая доля кликов реально дошла до Telegram, и недошедшие не искажают расчётную атрибуцию.

### Этап 3 — Рекламные интеграции (17 задач)

> Интеграции с рекламными системами и управление качеством отправляемых конверсий.

```

**Критерий готовности:** конверсия не теряется при сбое рекламного API и не уходит за подписчика, который отписался через минуту.

**Критерий готовности:** внешняя система может забрать источник конкретного человека по API.

> Нагрузка, устойчивость, роли, аудит и проверка гипотез.

**Критерий готовности:** 100 тысяч подписчиков, год данных и несколько каналов — интерфейс остаётся быстрым.

## 5. Как принимается решение по каждой задаче

**Бэклог из Excel — не список обязательных задач.** Перед реализацией каждый ID проходит три шага.

### Шаг 1. Проверить старый кабинет

Есть ли такой функционал? Смотреть [`OLD_DASHBOARD_ANALYSIS.md`](./OLD_DASHBOARD_ANALYSIS.md) **и код** — оценки аудита от 2026-07-20 местами устарели.

Если есть: найти реализацию, понять архитектуру, оценить, годится ли логика.

### Шаг 2. Принять решение

| Вариант | Статус в `MIGRATION_MAP.md` |
|---|---|
| Переносим существующую реализацию | `MIGRATE` |
| Старая архитектура плохая — делаем заново | `REBUILD` |
| Функции нет — создаём с нуля | `NEW` |
| Функция больше не нужна | `REMOVE` |

Решение и причина записываются в [`DECISIONS.md`](./DECISIONS.md).

### Шаг 3. Только после этого писать код

Перед началом — заполнить [`current-task.md`](./current-task.md): что делаем, зачем, сценарий, какие старые функции проверены, какие файлы затрагиваем, как тестируем.

## 6. Границы

### Новый кабинет **не** делает

- Не переписывает движок атрибуции, захват клика, доставку конверсий и retention — это переиспользуется как есть.
- Не создаёт новые таблицы там, где схема уже покрывает задачу.
- Не ломает публичные маршруты `/l/:slug`, `/r/:slug` и Telegram webhook.
- Не переносит LOCAL_MODE (демо-эмуляция на localStorage).
- Не копирует старую навигацию.

### Вне бэклога вообще

Биллинг, Telegram Mini App, антифрод, конструктор лендингов, мультиязычность. Появятся только через отдельное решение в `DECISIONS.md`.

## 7. Критерий успеха

> Не количество функций, а понятная архитектура, понятные процессы и понятный продукт.

Проверяется так:

1. Новый разработчик читает `PROJECT_CONTEXT.md` и понимает продукт без объяснений.
2. Для любой функции есть ответ, кому она нужна и какую проблему решает.
3. Каждый экран отвечает на вопрос пользователя, а не показывает данные «как есть».
4. Сумма по источникам сходится с реальным приростом канала.
5. Старый кабинет продолжает работать, пока новый его не заменит.
