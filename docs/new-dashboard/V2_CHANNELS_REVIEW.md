### Статусы канала

Пользователю не показываются `isActive` и `botIsAdmin` — показывается вывод.

| Статус | Условие | Что видит пользователь |
|---|---|---|
| **Працює** | `isActive && botIsAdmin` | «Підписки й відписки фіксуються автоматично» |
| **Потребує уваги** | `isActive && !botIsAdmin` | «Бот не адміністратор — Telegram не повідомляє нам про підписки» + 3 шага |
| **Відключено** | `!isActive` | «Збір зупинено. Історія збережена» + «Відновити збір» |

Живая проверка уточняет статус: если бот админ, но право «Додавання учасників» выключено — это «Потребує уваги», хотя в БД `botIsAdmin = true`. Список этого не видит, потому что `GET /api/channels` не возвращает `canInviteUsers`.

Все существующие. **Ни один не изменён, новых не создано.**

| Эндпоинт | Метод | Где |
|---|---|---|
| `/api/channels` | GET | Загрузка списка (server component) |
| `/api/channels/:id/bot-status` | GET | Кнопка «Перевірити» |
| `/api/channels/:id/archive` | PATCH | Архивация |
| `/api/channels/:id/activate` | PATCH | Восстановление |

## Найденные проблемы старого кабинета

Обе найдены при разработке. **Старый кабинет не трогали** — фиксируем для отдельной задачи.

### 1. Архивация в старом кабинете не работает

`PATCH` отправляется с заголовком `Content-Type: application/json`, но без тела. Fastify отвечает **400**: «Body cannot be empty when content-type is set to 'application/json'».

Проверено напрямую:

```
PATCH /api/channels/:id/archive  + Content-Type  → HTTP 400
PATCH /api/channels/:id/archive  без Content-Type → HTTP 200
```

Затронуто в [lib/actions.ts](../../apps/web/src/lib/actions.ts): `setTrackingLinkActiveAction` (строка 208), `setChannelActiveAction` (237), `revokeSeedInviteLinkAction` (288). То есть архивация ссылок, архивация каналов и отзыв invite-ссылок в старом кабинете возвращают ошибку.

В v2 исправлено: `Content-Type` добавляется только к запросам с телом.

### 2. Ручное подключение канала в старом кабинете не работает

[SyncChannelForm.tsx](../../apps/web/src/components/SyncChannelForm.tsx) делает клиентский `fetch('/api/channels/sync-telegram')`. Прокси `/api/[...path]` передаёт заголовки браузера как есть и не добавляет `Authorization` — а [jwt-auth.guard.ts](../../apps/api/src/common/guards/jwt-auth.guard.ts) читает только его.

```
GET /api/channels через прокси (cookie)      → 401
GET /api/channels напрямую (Authorization)   → 200
```

В v2 всё идёт через server actions.

Запуск через `tsx` без браузера и БД:

```
✓ активный канал, бот админ          → working    «Працює»
✓ бот потерял права                  → attention  «Потребує уваги»
✓ канал архивирован                  → archived   «Відключено»
✓ архивирован + нет прав             → archived   «Відключено»
✓ live: всё ок                       → working    «Працює»
✓ live: админ БЕЗ права инвайтов     → attention  «Потребує уваги»
✓ live: не админ                     → attention  «Потребує уваги»
✓ live на архивном                   → archived   «Відключено»
```

| Вопрос | Где ответ |

## Замечание по процессу

`next build` во время работающего `next dev` перезаписывает `.next` и ломает dev-сервер: `/v2/channels` начал отдавать 500 с `MODULE_NOT_FOUND`. Это артефакт инструментов, а не кода — после `rm -rf .next` и перезапуска dev-сервера всё вернулось к 200, production-сборка при этом проходила успешно.

**Вывод:** не запускать `next build` параллельно с `next dev` на одном каталоге.
